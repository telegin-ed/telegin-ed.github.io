# C# Concurrency. Асинхронное программирование и многопоточность

## Part I. Основы асинхронного программирования и многопоточности

### Глава 1. Асинхронное программирование и многопоточность

Многопоточность создаёт видимость одновременного выполнения, даже когда количество задач превышает количество ядер процессора. Асинхронное программирование оптимизирует использование процессора.

#### Итоги главы

> - Многопоточность — это настолько быстрое переключение между несколькими потоками, которые выполняются на одном и том же процессоре, что создается ощущение, будто все они выполняются одновременно.
> - Поток — это последовательность команд, которые могут обрабатываться в один и тот же момент времени только одним ядром процессора.
> - Поток имеет значительные накладные расходы.
> - Переключение между потоками называется переключением контекста и тоже имеет накладные расходы.
> - При операциях ввода-вывода за пределами процессора поток ожидает завершения операции. Такие операции называются блокирующими.
> - Асинхронное программирование не блокирует поток. Такие операции называются неблокирующими.
Позже, когда данные станут доступны, программа сможет продолжить обработку, обычно в другом потоке.
> - Асинхронные и многопоточные подходы к реализации программ совершенно необходимы, поскольку сложность программного обеспечения растет быстрее, чем однопоточная производительность процессоров.
> - Асинхронные методы снижают затраты в облачных вычислениях.

### Глава 2. Компилятор переписывает ваш код

Компилятор изменяет код, то есть результат компиляции не является прямым представлением исходного кода. Это нужно для сокращения шаблонного кода и добавления возможностей, недоступных в .NET.

Одной такой возможностью являются операторы `async`/`await`, реализуемые компилятором C#.

#### Итоги главы

> - Компилятор C# реорганизует и переписывает код, для расширения возможностей, отсутствующих в .NET.
> - Для реализации лямбда-функций компилятор перемещает их код в новый метод, и общие данные выносятся в отдельный класс.
> - Для реализации `yield return` компилятор делит исходный код на фрагменты и заключает их в класс, который запускает требуемый фрагмент в нужное время, для имитации приостановки и возобновления.

### Глава 3. Ключевые слова async и await

`async`/`await` — это инструкции, позволяющие писать асинхронный код, как если бы это был обычный синхронный код.

`Task` сообщает о завершении фоновой операции (событие), а `Task<T>` хранит результат фоновой операции и предоставляет возможность получить его.

В терминологии .NET/C# говорится, что задача завершена, когда наступило событие, представляемое объектом `Task`, или стал доступно значение, представляемое объектом `Task<T>`.

Объекты `Task` или `Task<T>` представляют событие или результат, которые могут произойти в будущем. Два способа определения завершения: опрос состояния (`Task.IsCompleted`), генерация события (`ContinueWith`).

Синхронный вариант - использование `Task.Wait`, `Task<T>.Result` неэффективно, потому что сводит на нет преимущества использования асинхронного подхода.

После завершения задачи нужно проверить, была она выполнена успешно или нет. Классы `Task` и `Task<T>` содержат свойства `IsFaulted`, `IsCanceled` и `IsCompletedSuccessfully`.

`async`/`await` разбивают код на части (как `yield return`) через `ContinueWith`.

Методы `async void` работают по принципу «запустил и забыл» — часто используются как обработчики событий.

Методы `async void` должны использоваться только для обработчиков событий и не должны генерировать никаких исключений.

`Dictionary` не является потокобезопасным и не может использоваться в асинхронных методах

`ValueTask<T>` — структура, которая содержит непосредственное значение, если оно доступно немедленно, и ссылку на `Task<T>` в противном случае

#### Итоги главы

> - `Task` представляет событие, которое может произойти в будущем.
> - `Task<T>` представляет значение, которое может быть доступно в будущем.
> - Когда событие происходит или значение становится доступно, говорится, что задача завершилась.
> - Свойства `IsCompleted` и `Status` можно использовать для проверки завершения задачи.
> - Следует использовать `ContinueWith`, чтобы задача уведомила о своем завершении.
> - Можно вызвать `Wait` или `Result`, чтобы выполнить задачу синхронно, но это неэффективно и опасно.
> - Вызов `Wait` или `Result` после завершения задачи совершенно безопасен и эффективен.
> - `async` — это просто флаг, сообщающий компилятору, что метод нужно разбить на части, если в нем обнаружится ключевое слово `await`.
> - Ключевое слово `async` не запускает выполнение в фоне.
> Без `await` `async` не влияет на работу кода (только генерирует шаблонный код).
> - Компилятор разбивает метод на части после каждой инструкции `await` и (концептуально) передает следующую часть в вызов `ContinueWith`.
> - `await` ничего не ждет, завершает текущую часть и возвращает управление вызывающему коду.
> - Методы `async` могут возвращать тип `void`, без возможности отслеживания завершения — все исключения должны перехватываться внутри.
> - Если `async`-метод часто немедленно возвращает результат, не выполняя асинхронных операций, то `ValueTask` или `ValueTask<T>` вместо использования `Task` или `Task<T>` повышает эффективность.

### Глава 4. Основы многопоточности

#### Способы запуска кода в другом потоке

##### Thread.Start

```c#
public void RunLotsOfThreads()
{
    var threads = new Thread[100];
    for(int i=0;i<100;++i)
    {
        threads[i] = new Thread(MyThread);
        threads[i].Start(i);
    }
    foreach(var current in threads)
    {
        current.Join();
    }
    Console.WriteLine("Выполнено");
}

private void MyThread(object? parameter)
{
    Console.WriteLine($"Привет из потока {parameter}");
}
```

Класс `Thread` также содержит метод `Join`, который будет ждать завершения потока.

Класс `Thread` имеет методы `Suspend`, `Resume` и `Abort`, использование которых опасно — можно вызвать взаимоблокировку.

`Suspend` может произойти в любой момент, например, когда поток находится в середине операции выделения памяти и удерживает блокировку внутри диспетчера памяти. Если другой поток, который должен вызвать `Resume`, попытается выделить память это приведет к взаимоблокировке.

`Thread.Start` применяется:
- для долго выполняющегося кода;
- если нужно изменить свойства потока, например - информацию о языке и локали, признак выполнения в фоне, COM-апартаменты и т. д. (обо всех настройках потока мы поговорим ближе к концу этой главы).

`Thread.Start` не рекомендуется применять для:
- асинхронного кода;
- коротких задач.

##### Пул потоков

Пул потоков — это решение, направленное на уменьшение накладных расходов на создание и уничтожение потоков. Это оптимальное решение для выполнения коротких задач.

```c#
public void RunInBackground()
{
    for(int i=0;i<10;++i)
    {
        ThreadPool.QueueUserWorkItem(RunInPool,i);
    }
}

private void RunInPool(object? parameter)
{
    Console.WriteLine($"Привет из потока {parameter}");
}
```

В отличие от класса `Thread` с его методом `Join`, пул потоков не имеет встроенного способа ожидания завершения выполняемого кода.

`ThreadPool.QueueUserWorkItem` применяется для:
- коротких задач.

`ThreadPool.QueueUserWorkItem` не рекомендуется использовать:
- для долго выполняющихся задач;
- когда нужно изменить свойства потока;
- с асинхронными операциями на основе `Task`;
- с инструкциями `async`/`await`.

##### Task.Run

Пул потоков идеально подходит для асинхронного кода, но проблема в том, что метод `QueueUserWorkItem` не использует класс `Task`. `Task.Run` запускает код в пуле потоков, подобно `ThreadPool.QueueUserWorkItem`, но имеет более удобный интерфейс, поддерживающий `async`/`await`.

```c#
public async Task RunInBackground()
{
    var tasks = new Task[10];
    for(int i=0;i<10;++i)
    {
        tasks[i] = Task.Run(RunInPool);
    }
    await Task.WhenAll(tasks);
    Console.WriteLine("Все выполнено");
}

private void RunInPool()
{
    Console.WriteLine("Делаем что-то");
}
```

Завершение задач можно ждать с помощью `Task.WhenAll`.

Когда метод `Task.Run` используется без `await`, компилятор выдает предупреждение, но добавление `await` перед `Task.Run` почти всегда является неверным решением - это говорит компилятору, что нужно дождаться завершения задачи, прежде чем переходить к следующей строке кода, в результате чего код выполняется синхронно.

Для устранения предупреждения можно присвоить `Task`, возвращаемый методом `Task.Run`, в специальную переменную-заполнитель:

```c#
_ = Task.Run(MethodToRunInBackground);
```

`Task.Run` не имеет параметризованной версии, но для его имитации и передачи данных в запускаемый код можно использовать лямбда-функции.

```c#
public void RunInBackground()
{
    for(int i=0;i<10;++i)
    {
        var icopy = i;
        Task.Run(()=>
        {
            Console.WriteLine($"Привет из потока {icopy}");
        });
    }
}
```

Здесь переменную `icopy` необходимо объявить внутри цикла, иначе все задачи получат финальное значение `i`, поскольку для запуска задачи требуется некоторое время и к моменту начала их выполнения цикл уже завершится.

Когда использовать `Task.Run`:
- для кода, использующего `async`/`await`;
- коротких задач.

Не рекомендуется использовать `Task.Run` для:
- синхронных задач, выполняющихся продолжительное время.

#### Доступ к одним и тем же переменным из нескольких потоков

Возможные решения:
- не использовать общие данные, доступные нескольким потокам
- не изменять общие данные
- использование блокировок и мьютексов

В C# есть класс `Mutex`, реализующий поддержку мьютексов операционной системы, и инструкция `lock`, которая проще в использовании и быстрее (потому что не требует применения системных вызовов).

В инструкцию `lock` нужно передавать объект, который может быть любым, но принято передавать закрытое поле класса. В .NET 9 и более поздних версиях лучше использовать объект `System.Threading.Lock` - его реализация в новых версиях может оказаться эффективнее, чем `Object`.

Взаимоблокировка — это ситуация, когда поток или несколько потоков блокируются в ожидании чего-то, что никогда не произойдет.

#### Ожидание другого потока

Иногда нужно, чтобы один поток дождался, когда другой поток что-то сделает. Если нужно дождаться, когда созданный поток завершит работу, можно использовать `Thread.Join`. Но если другой поток должен продолжить работу, нужно выбрать другой механизм, например `ManualResetEventSlim` - это обновленная версия `ManualResetEvent`. Как и все классы, заканчивающиеся на `Slim`, он лишен некоторой функциональности, в основном поддержки межпроцессных взаимодействий, ради улучшенной производительности.

```c#
var myEvent = new ManualResetEventSlim(false);
var threadWeWaitFor = new Thread(()=>
{
    Console.WriteLine("Делаем что-то");
    Thread.Sleep(5000);
    Console.WriteLine("Выполнено");
    myEvent.Set();
});

var waitingThread = new Thread(()=>
{
    Console.WriteLine("Ожидаем другой поток, чтобы что-то сделать");
    myEvent.Wait();
    Console.WriteLine("Другой поток закончил выполнение, продолжаем");
});

threadWeWaitFor.Start();
waitingThread.Start();
```

#### Другие методы синхронизации

В дополнение к двум методам синхронизации потоков - инструкции `lock` и классу `ManualRestEventSlim` - в .NET имеется обширная коллекция других примитивов синхронизации. Каждый из них полезен в конкретных обстоятельствах. И все они имеют одну общую черту: в большинстве случаев их следует избегать.

Например, класс `Interlocked`, предлагает потокобезопасные операции не требующие блокировки, но имеет ограничения:
- поддерживает только ограниченный набор операций, а именно: приращение, уменьшение и сложение, а также побитовые операции И и ИЛИ для некоторых целочисленных типов (`int`, `uint`, `long` и `ulong`)
- остальные операции могут быть реализованы с применением методов `Exchange` и `CompareExchange`
- защищает операцию, а не переменную. Даже если нужно прочитать переменную, не изменяя ее, то нужно использовать `Interlocked.Read`. Если кто-то обращается к переменной, «защищенной» блокируемой операцией, с помощью других инструментов, кроме членов класса `Interlocked`, то все гарантии отменяются и код перестает быть потокобезопасным.
- Значение, которое возвращают методы `Interlocked`, гарантированно является правильным на момент вызова метода, но к моменту использования этого значения, даже если это происходит в той же строке кода, значение может устареть.
- Потокобезопасным является только один вызов метода класса `Interlocked`. Если, к примеру, дважды вызвать `Interlocked.Increment`, то другой поток, может прочитать или изменить любую из переменных между этими двумя операциями.
- Члены класса `Interlocked` работают быстрее, чем инструкция `lock`, но они могут оказаться значительно медленнее обычных операций.

#### Параметры потока

Изменять параметры потоков допускается только в том случае, если эти потоки создаются вашим кодом с помощью класса `Thread`.

##### Режим выполнения потока в фоне

Устанавливается с помощью свойства `Thread.IsBackground` и влияет на выбор момента, когда приложение сможет завершить работу. Это произойдет, когда завершатся все нефоновые потоки. То есть если с помощью класса `Thread` запустить поток (и не установить его свойство `IsBackground`), то после завершения метода Main, приложение продолжит работу до тех пор, пока не завершится данный поток. Cвойство `Thread.IsBackground` должно устанавливаться до вызова `Thread.Start` .

##### Язык и локаль

Можно изменить с помощью свойства `Thread.Current­Culture`.

##### Текущий пользователь

Это свойство фактически (неофициально) устарело. Для присоединения идентификатора и разрешений к потоку можно использовать статическое свойство
`Thread.CurrentPrincipal`. Однако изменение этого свойства не изменяет разрешений потока на уровне операционной системы. Это просто место, где можно хранить информацию о пользователе.

В ASP.NET Classic (в .NET Framework 4.x и в более ранних версиях) при использовании встроенной системы аутентификации текущая информация о веб-пользователе сохранялась в свойстве `CurrentPrincipal`. В ASP.NET Core (.NET Core и .NET 5 и более поздних версиях) ситуация изменилась: в новой версии информация о текущем пользователе хранится только в `HttpContext.User`.

##### Приоритет потока

Следует избегать. Слишком легко попасть в ситуацию, когда поток с высоким приоритетом ждет освобождения ресурса, удерживаемого потоком с низким приоритетом, но этот низкоприоритетный поток не может освободить ресурс, потому что все процессорное время отдается высокоприоритетному потоку.

#### Итоги главы

> - Несколько задач можно запускать параллельно. Каждая задача — это поток.
> - В начальный момент программа запускает один поток, в котором выполняется метод Main. Этот поток называется главным потоком.
> - Потоки можно создавать через `Thread`, контролируя их параметры. Запуск выполняется с помощью метода `Thread.Start`.
> - Пул потоков — это коллекция потоков, управляемых системой, которые можно использовать для параллельного запуска своего кода. Пул потоков оптимизирован для выполнения коротких задач и может создавать новые потоки по мере необходимости.
> - Традиционно запуск кода в пуле потоков производится с помощью метода `ThreadPool.QueueUserWorkItem`.
> - Более простой и дружественный к `async`/`await` способ запуска кода в пуле потоков — вызов метода `Task.Run`.
> - Главный поток и потоки, создаваемые с помощью класса `Thread` полностью контролируются.
> - При доступе к общим данным из нескольких потоков необходимо использовать блокировку, в привочном случае разные потоки могут искажать данные.
> - В приложениях с графическим интерфейсом есть отдельный поток UI — поток пользовательского интерфейса.

### Глава 5. async/await и многопоточность

Асинхронное программирование — это выполнение действий (например, чтение файла или ожидание получения данных по сети), которые не требуют участия процессора и происходят в фоновом режиме, при этом процессор используется для выполнения каких-то других действий. Многопоточность — это выполнение действий с использованием или без использования процессора в фоновом режиме, при котором процессор задействуется для выполнения каких-то других действий.

```c#
public async Task Process10Files()
{
    var tasks = new Task[10];
    for(int i=0;i<10;++i)
    {
        var icopy = i;
        tasks[i] = Task.Run(async ()=>
        {
            await File.ReadAllBytesAsync($"{icopy}.txt");
            Console.WriteLine("Выполнение действий с содержимым файла");
        });
    }
    await Task.WhenAll(tasks);
}
```

В примере программа освободит вызывающий поток, вызывающий Process10Files, и не будет использовать другие потоки, пока не прочитает хотя бы один файл.

Вместо того чтобы получить десять потоков и сразу заблокировать их на все время выполнения чтения, код возьмет поток из пула, запустит в нем асинхронную операцию чтения, затем освободит поток и использует механизм обратного вызова. То есть будет использоваться небольшое количество потоков для запуска операций чтения, а затем вообще не будет использовать потоки во время ожидания (поток, вызвавший Process10Files уже был освобожден).

Освободив все потоки на время ожидания получения данных, программа должна продолжить работу, когда данные поступят, но сделать это в том же потоке уже не получится - поток уже был освобожден. Код после `await` запускается в обратном вызове `ContinueWith` в другом потоке.

`await` пытается запустить код в том же потоке, который его вызвал, поэтому в большинстве случаев нет необходимости задумываться о возможности смены потока. Если `await` не может использовать тот же поток, то вместо этого он будет использовать пул потоков. Ниже перечислены конкретные правила, которым он при этом следует.

- При использовании `await` в потоке пользовательского интерфейса (WinForms, WPF или UWP), код после `await` будет выполняться в том же потоке.
- При использовании `await` при обработке запроса в ASP.NET Classic (.NET Framework 4.8 и более ранних версий), то код после `await` будет выполняться в том же потоке.
- Если код или используемый фреймворк изменяют `SynchronizationContext` или `TaskFactory` текущего потока, то `await` будет использовать их. Именно так фреймворки, упомянутые в предыдущих пунктах, управляют поведением `await`, но за исключением фреймворков пользовательского интерфейса это случается крайне редко.
- Во всех остальных случаях код после `await` будет запущен в пуле потоков.

Эти правила применяются, только если `await` должен ждать завершения. Если к моменту вызова `await` операция уже завершилась, то почти во всех случаях код просто продолжит работу в текущем потоке.

Пример асинхронного запроса с кешированием, который не скомпилируется:

```c#
private Dictionary<string,string> _cache = new();
private object _cacheLock = new();
public async Task<string> GetResult(string query)
{
    lock(_cacheLock)
    {
        if(_cache.TryGetValue(query, out var cacheResult)
            return cacheResult;
        var http = new HttpClient();
        var result = await http.GetStringAsync("https://example.com?"+query);
        _cache[query] = result;
    }
    return result;
}
```

Здесь две проблемы:

- Концептуальная проблема - вызов `await` освобождает поток и возвращает его в пул, поэтому неизвестно, какой код будет запущен в этом потоке. Это проблема, потому что, запуск кода, который не контролируется, при удерживаемой блокировке может привести к состоянию взаимоблокировки.
- Практическая проблема - код после `await` может выполняться в другом потоке, тогда как реализация инструкции `lock` позволяет снять блокировку, только если это происходит в том же потоке, который ее установил.

Решение: реорганизовать код так, чтобы вызов `await` производился вне блока `lock`.

```c#
private Dictionary<string,string> _cache = new();
private object _cacheLock = new();
public async Task<string> GetResult(string query)
{
    lock(_cacheLock)
    {
        if(_cache.TryGetValue(query, out var cacheResult)
            return cacheResult;
    }
    var http = new HttpClient();
    // ошибка компиляции из-за await
    var result = await http.GetStringAsync("https://example.com?"+query);
    lock(_cacheLock)
    {
        _cache[query] = result;
    }
    return result;
}
```

Но и этот код имеет проблему: несколько потоков могут пройти первый `lock` и перезаписать кэш. В большинстве случаев это не проблема, так как перезапись одинакового значения безопасна.

#### Итоги главы

> - Асинхронные операции позволяют запускать многопоточные операции.
> - Высокопроизводительный многопоточный код также выиграет от асинхронных операций.
> - В UI-приложениях код после `await` выполняется в потоке UI.
> - В остальных случаях код после `await` выполняется в пуле потоков (за исключением случаев, когда такое поведение переопределяется с помощью `SynchronizationContext` или `TaskFactory`).
> - При выполнении кода, вызывающего `await`, в пуле потоков, код после `await` может быть запущен в другом потоке из того же пула потоков.
> - Внутри `lock` нельзя использовать `await` — лучше вынести его наружу.

### Глава 6. Когда использовать async/await

Преимущества `async`/`await`:

- способность обрабатывать более высокие нагрузки
- меньшее количество используемых ресурсов даже при низких нагрузках
- простота использования многопоточности в сочетании с кодом, который должен выполняться в определенном потоке

Недостатки `async`/`await`:

- Асинхронное программирование заразно - Любой код, вызывающий асинхронный код, сам должен быть асинхронным.
- Асинхронное программирование имеет больше пограничных случаев - добавляются новые пограничные случаи и варианты сбоев, которые не возникают в синхронном однопоточном коде.
- Многопоточность имеет еще больше пограничных случаев.
- `async` /`await` — дорогое удовольствие по сравнению с однопоточным кодом. Компилятор генерирует много вспомогательного кода, чтобы сделать код асинхронным.

Когда использовать `async`/`await` (рекомендации отсортированы в порядке убывания важности):

- Если код управляет большим количеством подключений одновременно, то `async`/`await` следует использовать всегда, когда это возможно.
- При работе с асинхронным API `async`/`await` следует использовать всегда, когда используется этот API.
- При возникновении проблемы с зависанием интерфейса в приложении с графическим интерфейсом следует использовать `async`/`await`.
- Асинхронность полезна при длительных операциях ввода-вывода.
- В приложении, широко использующем `async`/`await`, следует указывать `async`/`await` только там, где это имеет смысл.
- В приложении, не использующем `async`/`await`, следует избегать этих инструкций по мере возможности.
- При написании кода, выполняющего только одну операцию, не следует использовать `async`/`await`.
- Во всех остальных случаях следует внимательно рассмотреть возможные компромиссы и принять обоснованное решение.

#### Итоги главы

> - Асинхронный код может справляться с гораздо большей нагрузкой, чем синхронный код, используя при этом значительно меньше ресурсов.
> - Когда важно запустить код в определенном потоке, `async`/`await` упрощает использование многопоточности и асинхронных вызовов.
> - Асинхронный код имеет недостатки:
>     - код, вызывающий асинхронные методы, сам должен быть асинхронным;
>     - асинхронный код более подвержен ошибкам, чем синхронный однопоточный код;
>     - многопоточный код более подвержен ошибкам, чем однопоточный;
>     - для асинхронных методов генерируется больше кода, чем для синхронных;

### Глава 7. Классические ловушки многопоточности и как их избежать

#### Частичное обновление

Частичное обновление происходит, когда один поток обновляет некоторые данные, а в середине этого обновления другой поток читает данные и видит смесь старых и новых значений.

Иногда проблема может быть очевидна - изменение нескольких переменных. Но проблема может возникнуть и в таком коде:

```c#
void SetPrice(decimal newPrice)
{
    _price = newPrice;
}
```

Здесь проблема в том, что decimal имеет размер 128 бит, а в 64-битных процессорах доступ к памяти осуществляется блоками по 64 бита. Аналогично с long, который имеет размерность 64 бита, но если операционная система 32-битная, также может быть проблема частичного обновления.

Решение заключается в использовании механизма блокировки, а самый простой механизм блокировки в C# — это инструкция `lock`.

#### Изменение порядка доступа к памяти при компиляции

В современных архитектурах доступ к памяти медленнее обработки данных в процессоре, и различные шаблоны доступа к памяти влияют на производительность. Для повышения производительности компилятор может изменить порядок операций.

Пример псевдокода увеличения переменной в цикле:

```text
Записать 0 в регистр (быстро)
Сохранить значение из регистра в память в переменную "counter" (медленно)
for(int i;i<100;++i)
{
    Загрузить значение из памяти с переменной "counter" в регистр (медленно)
    Увеличить значение в регистре (быстро)
    Сохранить значение из регистра в память в переменную "counter" (медленно)
}
```

Оптимизированный вариант:

```text
Записать 0 в регистр (быстро)
for(int i;i<100;++i)
{
    Увеличить значение в регистре (быстро)
}
Сохранить значение из регистра в память в переменную "counter" (медленно)
```

Общее правило заключается в том, что компилятору разрешено вносить любые изменения, которые не изменяют конечный результат в однопоточной среде.

Следующий пример демонстрирует удаление кода: в однопоточной среде _doingSomething всегда на выходе будет иметь значение `false`.

```text
if(_doingSomething) return;
_doingSomething = true;
// выполнить какие-то действия
_doingSomething = false;
```

Оптимизированный вариант:

```text
if(_doingSomething) return;
// выполнить какие-то действия
_doingSomething = false;
```

В действительности ситуация еще хуже, потому что доступ к памяти компьютера осуществляется очень медленно. У процессора есть своя внутренняя кеш-память, меньшая по объему и более быстрая (но все равно более медленная, чем регистры).

Невозможно написать правильный многопоточный код, когда любое обращение к памяти может быть перемещено или удалено. Существуют инструменты, ограничивающие систему в вариантах перемещения операций доступа к памяти. Есть операции, которые говорят системе: «Не выполняй операцию чтения раньше этой точки». Это называется семантикой захвата. Есть операции, которые говорят системе: «Не выполняй операцию записи позднее этой точки». Это называется семантикой освобождения.

```c#
// ...
lock (_lock)
// При входе в блок lock включается семантика захвата, поэтому чтение x из памяти не может быть выполнено до этой точки
{
    // Чтение x может происходить в любой точке этого диапазона
    // ...
    if (x == 5)
    {
        // запись x может происходить в любой точке этого диапазона
        x = 6;
    }
    // ...
    // При выходе из блока lock включается семантика освобождения, поэтому запись значения в x не может быть выполнена после этой точки
}
```

Существуют также операции, не позволяющие компилятору перемещать обе операции, чтения и записи, в любом направлении. Они называются барьерами памяти.

Первое правило: всегда следует использовать блокировку при доступе к общим данным.

#### Взаимоблокировки

Взаимоблокировка - это ситуация, когда поток блокируется в ожидании ресурса, который никогда не станет доступным из-за действий этого же потока.

Пример кода, который может привести к взаимоблокировке:

```c#
public int Multiply()
{
    // Сначала блокируется левый операнд, затем правый
    lock(_leftOperandLock)
    {
        lock(_rightOperandLock)
        {
            return _leftOperand * _rightOperand;
        }
    }
}
public int Add()
{
    // Сначала блокируется правый операнд, затем левый
    lock(_rightOperandLock)
    {
        lock(_leftOperandLock)
        {
            return _leftOperand * _rightOperand;
        }
    }
}
```

Второе правило: блокировки всегда следует устанавливать в одном и том же порядке.

Третье правило: никогда не вызывать неподконтрольный код, удерживая блокировку.

```c#
public int Divide()
{
    lock(_leftOperandLock)
    {
        lock(_rightOperandLock)
        {
            // Условие изменено на обратное
            if(_rightOperand!=0)
            {
                // Если правый операнд не равен нулю, то метод завершится здесь
                return _leftOperand/_rightOperand;
            }
        }
    }
    // Вызов события после снятия блокировки
    DivideByZero?.Invoke(this, EventArgs.Empty);
    
    return 0;
}
```

Можно было бы подумать, что эту проблему можно решить, если никогда не удерживать более одной блокировки одновременно, но это не так, потому что в этом случае может возникнуть состояние гонки.

#### Состояние гонки

Состояние гонки возникает, когда результат кода зависит от возникновения неконтролируемых событий.

В коде ниже метод `Add` может выполниться между `lock(_leftOperandLock)` и `lock(_rightOperandLock)` метода `SetOperands`.

```c#
public int Add()
{
    int leftCopy,rightCopy;
    lock(_leftOperandLock)
    {
        leftCopy = _leftOperand;
    }
    lock(_rightOperandLock)
    {
        rightCopy = _rightOperand;
    }
    return rightCopy + leftCopy;
}
public int SetOperands(int left, int right)
{
    lock(_leftOperandLock)
    {
        _leftOperand = left;
    }
    lock(_rightOperandLock)
    {
        _rightOperand = right;
    }
}
```

Четвертое правило: блокировки должны удерживаться на протяжении всего выполнения операции.

С другой стороны блокировки нужно удерживать наименьшее время, т.к. долгое удержание приведет к другой проблеме - синхронизации.

#### Синхронизация

Синхронизация — это ситуация, когда операции происходят последовательно, а не параллельно.

Пятое правило: чтобы избежать синхронизации, нужно удерживать блокировки как можно более короткое время, желательно только на время, необходимое для доступа к общему ресурсу, а не в течение выполнения всей операции.

В некоторых ситуациях сокращение длительности удержания блокировки до любой величины, которая не вызывает синхронизацию, вызовет состояние гонки. В таких случаях следует помнить, что синхронизация может ухудшить производительность, а состояние гонки приведет к неправильным и неожиданным результатам. Поэтому состояние синхронизации выглядит предпочтительнее.

#### Голодание

Голодание — это ситуация, когда поток или группа потоков монополизирует доступ к некоторому ресурсу, не позволяя другому потоку или группе потоков выполнить какую-либо работу.

Если в программе есть высокоприо­ритетные потоки, которые не блокируются, они могут помешать выполнению низкоприоритетных потоков. Поведение в Windows и в Linux отличается - Linux не позволяет изменять приоритет потоков.

Шестое правило - не меняйте приоритет или привязку к процессору.

#### Итоги главы

> - Всегда следует использовать блокировки при доступе к общим данным.
> - Следует всегда устанавливать блокировки в одном и том же порядке - это называется *иерархией блокировок*.
> - Не следует вызывать неподконтрольный код, пока удерживается блокировка.
> - Объединение нескольких потокобезопасных операций редко дает объединенную потокобезопасную операцию.
> - Следует удерживать блокировки на всем протяжении выполнения операции.
> - Следует удерживать блокировки минимально возможное время.
> - Последние два пункта противоречат друг другу. Если золотой середины не существует, то лучше выбирать более долгие блокировки - состояние гонки обычно хуже.
> - Синхронизация иногда желательна. Некоторые операции должны выполняться последовательно.
> - Не менять приоритет потоков и процессов или привязку к процессору.

## Part II. Продвинутое использование async/await и многопоточности

### Глава 8. Обработка последовательности элементов в фоновом режиме

#### Параллельная обработка элементов

##### Один поток

```c#
void MailMerge(
string from,
string subject,
string text,
(string email,string name)[] recipients)
{
    var sender = new SmtpClient("smtp.example.com");

    // Цикл по списку получателей
    foreach(var current in recipients)
    {
        try
        {
            var message = new MailMessage();
            message.From = new MailAddress(from);
            message.Subject = subject;
            message.To.Add(new MailAddress(current.email));
            message.Body = text.Replace("{name}", current.name);
            sender.Send(message);
        }
        catch
        {
            LogFailure(current.email);
        }
    }
}
```

Если этот код работает в составе веб-приложения, у которого тайм-аут на веб-запрос составляет стандартные 30 сек, то с работой данного метода могут возникнуть проблемы уже с 10...40 получателями - синхронная отправка одного сообщения занимает значительное время.

##### Параллельная обработка элементов с помощью класса Thread

```c#
void MailMerge(
string from,
string subject,
string text,
(string email,string name)[] recipients)
{
    var processingThreads = new Thread[recipients.Length];
    for(int i=0;i< recipients.Length;++i)
    {
        processingThreads[i] = new Thread(()=>
        {
            try
            {
                var sender = new SmtpClient("smtp.example.com");
                var message = new MailMessage();
                message.From = new MailAddress(from);
                message.Subject = subject;
                message.To.Add(new MailAddress(recipients[i].email));
                message.Body = text.Replace("{name}", recipients[i].name);
                sender.Send(message);
            }
            catch
            {
                LogFailure(current.email);
            }
        });
        processingThreads[i].Start();
    }
    foreach(var current in processingThreads)
    {
        current.Join();
    }
}
```

Этот код создает поток для каждого отправляемого сообщения, запускает все потоки параллельно, а затем ожидает их завершения.

Недостатки - отсутствие ограничения на количество потоков. На современных производительных серверах проблемы могут начаться на 10000 одновременно запущенных потоках.

##### Параллельная обработка элементов с использованием пула потоков

```c#
void MailMerge(
string from,
string subject,
string text,
(string email,string name)[] recipients)
{
    var processingTasks = new Task[recipients.Length];
    for(int i=0;i< recipients.Length;++i)
    {
        // в отличии от ThreadPool.QueueUserWorkItem вызов Task.Run возвращает Task,
        // что упрощает отслеживание завершенных потоков
        processingTasks[i] = Task.Run(()=>
        {
            try
            {
                var sender = new SmtpClient("smtp.example.com");
                var message = new MailMessage();
                message.From = new MailAddress(from);
                message.Subject = subject;
                message.To.Add(new MailAddress(recipients[i].email));
                message.Body = text.Replace("{name}", recipients[i].name);
                sender.Send(message);
            }
            catch
            {
                LogFailure(current.email);
            }
        });
    }
    // Ожидает завершения
    Task.WaitAll(processingTasks);
}
```

Проблема потенциального создания огромного количества потоков здесь решена автоматически.

Пул ограничит количество потоков разумным для системы числом и избавит от накладных расходов на создание и уничтожение потоков. Однако возникает возможность перенасыщения пула потоков.

Если попытаться отправить те же 1000 сообщений, как в предыдущем примере, то пул окажется занятым до тех пор, пока все сообщения не будут отправлены, а весь остальной код, который тоже пользуется пулом потоков (например, ASP.NET), будет вынужден ждать.

Однако при нескольких запусках, или отправкой блоками по 1000 подписантов, производительность будет увеличиваться, т.к. пул потоков всегда автоматически оптимизирует количество потоков и будет ускоряться с каждой итерацией.

При разработке программы, требующей создания большого количества потоков в пуле, можно просто сообщить об этом системе и не ждать автоматических оптимизаций.

```c#
ThreadPool.GetMinThreads(out _, out var completionPortThreads);
ThreadPool.SetMinThreads(1000, completionPortThreads);
```

##### Асинхронная параллельная обработка элементов

В предыдущем примере было получено истощение пула потоков добавлением слишком большого количества длительно выполняющихся заданий. Все эти потоки просто блокируются и ничего не делают. Это именно та ситуация, в которой особенно хороши асинхронные техники.

```c#
void MailMerge(
string from,
string subject,
string text,
(string email,string name)[] recipients)
{
    var processingTasks = new Task[recipients.Length];
    for(int i=0;i< recipients.Length;++i)
    {
        // Добавлена инструкция async
        processingTasks[i] = Task.Run(async () =>
        {
            try
            {
                var sender = new SmtpClient("smtp.example.com");
                var message = new MailMessage();
                message.From = new MailAddress(from);
                message.Subject = subject;
                message.To.Add(new MailAddress(recipients[i].email));
                message.Body = text.Replace("{name}", recipients[i].name);
                // Добавлена инструкция await
                await sender.SendMailAsync(message);
            }
            catch
            {
                LogFailure(current.email);
            }
        });
    }
    Task.WaitAll(processingTasks);
}
```

##### Класс Parallel

Имеет четыре статических метода:

- `Invoke` - принимает массив делегатов и выполняет их все, по возможности параллельно. Возвращает управление после того, как все делегаты завершат работу. Использует тот же код, что и `ForEach`.
- `For` - действует как цикл for, но итерации выполняются параллельно. Возвращает управление после того, как все итерации завершатся. Использует тот же код, что и `ForEach`.
- `ForEach` - действует как цикл `foreach`, но итерации выполняются параллельно. Возвращает управление после того, как все итерации завершатся.
- `ForEachAsync` — действует подобно `ForEach`, но роль тела цикла играет асинхронный метод. Он немедленно возвращает управление и задачу `Task`, которая завершится, когда все итерации завершатся.

```c#
void MailMerge(
string from,
string subject,
string text,
(string email,string name)[] recipients)
{
    var processingTasks = new Task[recipients.Length];
    Parallel.ForEach(recipients, (current,_) =>
    {
        try
        {
            var sender = new SmtpClient("smtp.example.com");
            var message = new MailMessage();
            message.From = new MailAddress(from);
            message.Subject = subject;
            message.To.Add(new MailAddress(current.email));
            message.Body = text.Replace("{name}", current.name);
            sender.Send(message);
        }
        catch
        {
            LogFailure(current.email);
        }
    });
}
```

Класс `Parallel` также поддерживает отмену задания, настройку планировщика и управление максимальным количеством заданий, обрабатываемых одновременно.

Код теста производительности:

```c#
for (int j = 0; j < 5; ++j)
{
    var items = Enumerable.Range(0, 1000).ToArray();
    var sw = Stopwatch.StartNew();
    Parallel.ForEach(items, (item)=>Thread.Sleep(1000));
    sw.Stop();
    Console.WriteLine(sw.ElapsedMilliseconds);
}
```

По умолчанию `Parallel.ForEach` ограничивает количество заданий, выполняемых параллельно, поэтому он не привел к такой сильной нагрузке на пул потоков, как код с `Task.Run`. Однако именно из-за самоограничения механизм пула потоков не создал достаточного количества потоков и последующие итерации с `Parallel.ForEach` выполнялись медленнее.

Если установить параметр `MaxDegreeOfParallelism` равным длине списка (и тем самым заставить `Parallel.ForEach` выполнять все задания одновременно), мы получим точно такие же характеристики производительности, как и в примере с `Task.Run`. Это противоречит официальной документации, в которой четко говорится, что по умолчанию используются все потоки, а установка `MaxDegreeOfParallelism` может только уменьшить их количество и никогда не увеличивает его.

```c#
Parallel.ForEach(items,
    new ParallelOptions { MaxDegreeOfParallelism = 1000 },
    (item)=>Thread.Sleep(1000));
```

Когда обнаруживается противоречие между наблюдаемым и задокументированным поведением, возникает проблема. Очевидно, что нельзя полагаться на документированное поведение, потому что оно не соответствует действительности. Но и надеяться на наблюдаемое поведение тоже рискованно, потому что любое обновление может исправить ошибку.

К сожалению, увеличение производительности не происходит при переключении с `Parallel.ForEach` к его `async`/`await`-совместимому аналогу `Parallel.ForEachAsync`. Проблема в том, что `Parallel.ForEachAsync` использует `MaxDegreeOfParallelism` как количество одновременно обрабатываемых заданий, а не как количество потоков. Например, код асинхронно ждет 1 секунду 1000 раз и у ноутбука 12 ядер. `Parallel.ForEachAsync` начнет обрабатывать первые 12 элементов, обработает их все ровно за 1 секунду, затем начнет обрабатывать следующие 12 элементов. Общее время работы составит 84 секунд (деление 1000 на 12 с округлением вверх дает 84). Такое поведение трудно оправдать, и если оно не изменится в будущей версии .NET, то рекомендуется избегать метод `Parallel.ForEachAsync` или, если есть особая необходимость его использовать, выбрать подходящее значение для `MaxDegreeOfParallelism`.

#### Последовательная обработка элементов в фоновом режиме

Все предыдущие примеры ожидали отправки всех сообщений, но ничего не делали с результатом. Можно было бы перенести операцию отправки в фоновый поток и вернуть ответ пользователю немедленно. По сути, если не ждать завершения обработки всех сообщений, то безразлично, сколько времени займет их отправка.

##### Последовательная обработка элементов в фоновом режиме с помощью класса Thread

```c#
void MailMerge(
string from,
string subject,
string text,
(string email,string name)[] recipients)
{
    // Создает поток здесь
    var processingThread = new Thread(()=>
    {
        var sender = new SmtpClient("smtp.example.com");
        foreach(var current in recipients)
        {
            // А не здесь
            try
            {
                var message = new MailMessage();
                message.From = new MailAddress(from);
                message.Subject = subject;
                message.To.Add(new MailAddress(current.email));
                message.Body = text.Replace("{name}", current.name);
                sender.Send(message);
            }
            catch
            {
                LogFailure(current.email);
            }
        }
    });
    processingThread.Start();
}
```

Если попытаться выйти из программы, то программа не завершится, пока поток не закончит отправку всех сообщений.

##### Паттерн очереди заданий и BlockingCollection

Если не волнует время, необходимое для отправки сообщений, то лучше просто использовать один поток или небольшое фиксированное количество потоков, которые займутся отправкой. Такой подход называется паттерном очереди заданий и реализуется путем создания очереди, в которую каждый поток может добавлять задания, и имеется выделенный набор потоков, обрабатывающих эти задания. Эти потоки реализуют простой цикл чтения следующего элемента из очереди и его обработки.

`BlockingCollection<T>` можно использовать несколькими способами, например как потокобезопасный `List<T>`. Но в данном примере рассматривается только сценарий использования `BlockingCollection<T>` в качестве очереди заданий, и в этом случае нужны только три метода:

- `Add` - добавляет новое задание в конец очереди.
- `CompleteAdding` - указывает, что добавление заданий прекращено и поток, обрабатывающий задания, может завершиться, когда обработает все задания очереди.
- `GetConsumingEnumerable` - возвращает объект, который можно исполь­зовать в цикле `foreach` для перебора всех элементов в очереди. Если очередь пуста, то `foreach` заблокируется до момента, пока в очередь не будет до­бавлено очередное задание или не будет вызван метод `CompleteAdding`.

```c#
public class MailMerger
{
    private record MailInfo(
    string from,
    string subject,
    string text,
    string email);
    BlockingCollection<MailInfo> _queue = new();

    public void Start()
    {
        var thread = new Thread(BackgroundProc);
        thread.Start();
    }

    public void Stop()
    {
        _queue.CompleteAdding();
    }

    public void MailMerge(
    string from,
    string subject,
    string text,
    (string email, string name)[] recipients)
    {
        foreach(var current in recipients)
        {
            _queue.Add(new MailInfo(
            from,
            subject,
            text.Replace("{name}", current.name),
            current.email));
        }
    }

    private void BackgroundProc()
    {
        var sender = new SmtpClient("smtp.example.com");
        foreach (var current in _queue.GetConsumingEnumerable())
        {
            try
            {
                var message = new MailMessage();
                message.From = new MailAddress(current.from);
                message.Subject = current.subject;
                message.To.Add(new MailAddress(current.email));
                message.Body = current.text.Replace("{name}", current.name);
                sender.Send(message);
            }
            catch
            {
                LogFailure(current.email);
            }
        }
    }
}
```

Здесь использован класс `Thread`, потому что поток работает продолжительное время - вероятно, он будет работать в течение всего времени выполнения программы - и при использовании пула потоков можно израсходовать один из потоков в пуле и лишить систему возможности повторно использовать его для чего-то еще. Класс `Thread` плохо работает с асинхронным кодом, но класс `BlockingCollection` не является асинхронным и не имеет асинхронной версии, которая не блокируется.

`BlockingCollection` хранится только в памяти.

##### Обработка важных элементов с помощью постоянных очередей

Постоянные очереди — это самые обычные очереди, но хранящиеся на диске, а не в памяти.

При использовании постоянной очереди чтение следующего задания и его удаление из очереди могут быть разными операциями. Это важно, поскольку позволяет определять, как будут развиваться события в случае сбоя.

Первый вариант - удалить задание из очереди только после его обработки, «доставкой не менее одного раза».

Второй вариант - удалить задание из очереди до его обработки, «доставка не более одного раза».

Третий вариант - иметь гарантию, что каждый элемент будет обработан один и только один раз, «доставка строго один раз». К сожалению, реализовать такую логику работы обычно невозможно.

В текущем примере потеря соединения с почтовым сервером после завершения отправки сообщения, но до получения подтверждения от сервера лишит возможности узнать, было ли отправлено сообщение. И код оказывается в ситуации, когда либо необходимо рискнуть и отправить сообщение дважды, либо рискнуть и не отправить его вообще.

Если выбирается семантика доставки не менее одного раза и в очереди появляется задание, обработка которого снова приводит к сбою программы, то программа застрянет в бесконечном цикле: запуск, чтение первого задания из очереди, сбой при попытке его обработать и перезапуск. Поэтому важно иметь что-то, что следит за сбоями в коде.

Задания, которые всегда вызывают сбой, называются ядовитыми (poison) сообщения­ми, и лучшей практикой считается сохранение их где-то еще (часто в другой постоянной очереди), чтобы иметь возможность проверить задание и найти причину сбоя. Очереди, в которых хранятся такие задания, а также задания, которые не были обработаны по другим причинам, часто называются очередями недоставленных сообщений.

#### Итоги главы

> - Для параллельной обработки можно использовать класс `Thread`. Это хорошее решение, но оно является ресурсоемким.
> - Пул потоков можно использовать с помощью `ThreadPool.QueueUserWorkItem` или `Task.Run`. Пул потоков достаточно эффективен и способен автоматически подстраиваться под характер использования. Но может потребоваться некоторое время, чтобы достичь пиковой производительности, если переложить на него слишком много работы. Этот недостаток можно смягчить с помощью настроек пула потоков, когда необходимое количество потоков известно заранее.
> - Пул потоков особенно эффективен при работе с асинхронным кодом.
> - Класс `Parallel` предлагает более простой синтаксис использования пула потоков, но если использовать его для обработки больших коллекций, то следует провести тестирование производительности, чтобы подобрать хорошее значение для `MaxDegreeOfParallelism`.
> - Если неважно сколько времени займет выполнение операции, и нужно просто освободить текущий поток, можно запустить последовательную обработку заданий в фоновом режиме.
> - Для организации фонового потока можно использовать класс `Thread` или пул потоков.
> - Для организации фонового потока лучше реализовать паттерн очереди заданий, например, на основе класса `BlockingCollection`.
> - При невозможности терять данные при сбое программы, следует использовать постоянную очередь. Ее можно реализовать вручную, на основе базы данных, или использовать специализированное решение для очередей, такое как RabbitMQ, AWS SQS или Azure Storage Queues.
> - Используя постоянные очереди, необходимо подумать о выборе между семантиками «доставка не менее одного раза» и «доставка не более одного раза». Необходимо также предусмотреть обработку неотправленных сообщений.

### Глава 9. Отмена фоновых заданий

Самый простой способ реализовать возможность завершения программы - пометить поток как фоновый. Процесс завершается, когда завершается последний поток, не отмеченный как фоновый.

```c#
thread.IsBackground = true;
```

Недостатки:
- его можно использовать только для отмены операции при завершении всей программы;
- фоновый поток будет остановлен на середине выполняемой им операции, что оставит программу в нестабильном состоянии.

Классы `CancellationToken` и `CancellationTokenSource` - стандартные классы для отмены фоновых заданий. По своей сути `CancellationToken` - это просто переменная типа bool (обернутая в потокобезопасный и устойчивый к злоупотреблениям класс).

```c#
var thread = new Thread(BackgroundProc);
// Создание CancellationTokenSource
var cancelTokenSource = new CancellationTokenSource();
// Получение токена для фонового потока
var shouldCancel = cancelTokenSource.Token;

thread.Start();
Console.ReadKey();
// Остановка фонового потока
cancelTokenSource.Cancel();

void BackgroundProc()
{
    int i=0;
    while(true)
    {
        if(!ACalculationThatTakesOneMinute(cancelTokenSource.Token))
            return;
        Console.WriteLine(i++);
    }
}

bool ACalculationThatTakesOneMinute(CancellationToken shouldCancel)
{
    var start = DateTime.UtcNow;
    var result = 0;
    while((DateTime.UtcNow - start).TotalMinutes < 1)
    {
        //Проверка признака отмены во внутреннем цикле
        if(shouldCancel.IsCancellationRequested)
            return false;

        result++;
    }
    return true;
}
```

#### Отмена с использованием исключения

Использование исключения позволяет упростить код, удалив вложенную проверку флага.

```c#
shouldCancel.ThrowIfCancellationRequested();
```

#### Получение обратного вызова, когда вызывающий код отменяет операцию

```c#
class MyCalculation
{
    void Start();
    void Cancel();
    event Action Complete;
}

void RunMyCalculation(CancellationToken cancel)
{
    var calc = new MyCalculation();
    cancel.Register(()=>calc.Cancel());
    // Регистрирует обратный вызов
    calc.Complete += CalcComplete();
    calc.Start();
}
```

Метод `CancellationToken.Register` регистрирует метод обратного вызова, который `CancellationToken` должен запустить при отмене. Многократный вызов Register приведет к запуску всех зарегистрированных методов обратного вызова при отмене `CancellationToken`. Вызов `Register`, когда `CancellationToken` уже отменен, немедленно выполнит метод обратного вызова. `Register` возвращает объект, который можно использовать для отмены регистрации обратного вызова.

#### Реализация тайм-аутов

Распространенным сценарием отмены являются тайм-ауты, когда операция отменяется, если не успела завершиться в течение определенного времени.

```c#
var cancelSource = new CancellationTokenSource();
// в миллисекундах
cancelSource.CancelAfter(30000);
// через TimeSpan
cancelSource.CancelAfter(TimeSpan.FromSeconds(30));
```

#### Комбинирование методов отмены

Комбинирование методов используется, если необходимо отменить операцию по разным причинам - например, пользовательская отмена или таймаут.

Статический метод `CancellationTokenSour­ce.CreateLinkedTokenSource` способен создать `CancellationTokenSource` из одного или нескольких объектов `CancellationToken`.

```c#
public async Task<string> GetTextFromServer(CancellationToken canceledByUser)
{
    // Создает CancellationTokenSource, которым мы можем управлять
    var combined = CancellationTokenSource.CreateLinkedTokenSource(canceledByUser);
    // Добавляет тайм-аут
    combined.CancelAfter(TimeSpan.FromSeconds(10));
    using(var http = new HttpClient())
    {
        // Использует новый токен
        return await http.GetStringAsync("http://example.com", combined.Token);
    }
}
```

#### Специальные токены отмены

Иногда, несмотря на то что возможность отмены операции не нужна, используемый API все равно требует `Cancellation­Token`. В таких случаях можете просто передать `CancellationToken.None`. В результате используется `CancellationToken`, который нельзя отменить. Аналогично - `new CancellationToken(false)`.

`new CancellationToken(true)` создаст уже отмененный `Cancellation­Token`. В обычном коде в этом нет особого смысла, но такой прием может пригодиться в модульных тестах.

#### Итоги главы

> - `CancellationToken` — стандартный способ отмены операций в .NET.
> - Класс `CancellationTokenSource` используется для создания и управления объектами `CancellationToken`.
> - `CancellationTokenSource.Cancel` используется для отмены операции, а `Cancel­lationToken.IsCancellationRequested` — для проверки отмены операции.
> - `CancellationToken` — это просто флаг.
> - Для вызова метода обратного вызова при отмене можно использовать `CancellationToken.Register`.
> - Для реализации тайм-аутов можно использовать `CancellationTokenSour­ce.CancelAfter`.
> - `CancellationTokenSource.CreateLinkedTokenSource` позволяет создать `CancellationTokenSource` из одного или нескольких существующих объектов `CancellationToken` и управлять им.
> - `CancellationToken.None` используется при необходимости передать `CancellationToken`, который никогда не отменится.

### Глава 10. Ожидаем собственные события

#### Знакомство с TaskCompletionSource

Обычно написание собственных асинхронных API бывает необходимо, чтобы адаптировать асинхронный API, основанный на механизме, отличном от `Task`, к использованию с оператором `await`, или чтобы получить возможность использовать `await` для асинхронного ожидания событий в приложении, использующим потокобезопасные структуры данных, совместимые с `async`/`await`.

В библиотеке .NET есть класс с именем `TaskCompletionSource<T>`. Он может создавать объекты `Task<T>` и имеет методы с именами `SetResult` и `SetException`.

`TaskCompletionSource` имеет свойство с именем `Task`, которое позволяет получить созданный им объект `Task`. Каждый экземпляр `TaskCompletionSource` управляет только одним объектом `Task`.

Изначально `Task` находится в состоянии `WaitingForActivation`, а свойства `IsCompleted`, `IsCompletedSuccessfully`, `IsCanceled` и `IsFaulted` имеют значение `false`. Применение инструкции `await` к новому объекту `Task` приведет к асинхронному ожиданию, а вызов `Wait` или чтение свойства `Result` заблокируется до завершения задачи.

```c#
public class TaskCompletionSourceDemo
{
    // Нет ключевого слова async
    private Task<int> BackgroundWork()
    {
        var tcs = new TaskCompletionSource<int>();
        // Выполняется в другом потоке
        Task.Run(()=>
        {
            // Задача должна завершиться здесь
        });
        // Возвращает Task<int>, а не int
        return tcs.Task;
    }

    public async Task RunDemo()
    {
        // Ждет завершения задачи
        var result = await BackgroundWork();
        Console.WriteLine(result);
    }
}
```

`TaskCompletionSource` имеет три группы методов, которые можно использовать для завершения задачи.

1. `SetResult` и `TrySetResult` завершат задачу `Task`, изменят ее состояние на `RanToCompletion`, а в случае `Task<T>` сохранят результат в объекте `Task<T>` (который можно будет получить с помощью `Task`.`Result` или `await`). После вызова `SetResult` или `TrySetResult` свойства `IsCompleted` и `IsCompletedSuccessfully` получат значение `true`.

2. `SetException` и `TrySetException` завершат задачу с состоянием `Faulted` и сохранят исключение или список исключений в объекте `Task`. Исключение или список исключений будут заключены в объект `AggregateException` и сохранены в свойстве `Task`.`Exception`. Применение `await` к `Task`, чтение свойства `Result` или вызов `Wait`() выбросят `AggregateException`. После вызова `SetException` или `TrySetException` свойства `IsCompleted` и `IsFaulted` получат значение `true`.

3. `SetCanceled` и `TrySetCanceled` завершат задачу `Task`, изменят ее состояние на `Canceled` и при необходимости сохранят токен отмены в объекте `Task`. Применение инструкции `await` к `Task`, чтение свойства `Result` или вызов `Wait()` выбросят исключение `TaskCanceledException`. Если передать токен отмены в `TrySetCanceled`, то он будет доступен в свойстве `TaskCanceledException.CancellationToken`. После вызова `SetCanceled` или `TrySetCanceled` свойства `IsCompleted` и `IsCanceled` получат значение `true`. Несмотря на то что `await` выбросит исключение, свойство `IsFaulted` объекта `Task` будет иметь значение `false`, а свойство `Exception` - значение `null`.

```c#
var tcs = new TaskCompletionSource<int>();
// отменяет задачу
tcs.SetCanceled();
// выбрасывает исключение
tcs.SetResult(7);

var tcs = new TaskCompletionSource<int>();
// отменяет задачу
tcs.TrySetCanceled();
// игнорируется, вернет false
tcs.TrySetResult(7);
```

#### Выбор потока для запуска продолжения

Код, выполняемый после асинхронной операции (после `await` или обратного вызова, переданного в `ContinueWith`), называется продолжением (*continuation*). Вызов любого метода `TaskCompletionSource`, завершающего `Task`, приведет к запуску продолжения (очевидно, в этом и есть весь смысл), и `TaskCompletionSource` позволяет решить - запустить ли продолжение немедленно в том же потоке, откуда был вызван метод класса `TaskCompletionSource`.

Если позволить продолжению запуститься немедленно, то оно может запуститься до возврата из `TrySetResult`. Например, следующий код потенциально может попасть в состояние взаимоблокировки:

```c#
lock(_valueLock)
{
    _taskSource.TrySetResult(_value);
}
```

Здесь предполагается, что используемое значение (результат задачи) защищено блокировкой, поэтому создается блокировка и вызывается `TrySetResult` со значением. Это может привести к тому, что пока удерживается блокировка, будет в другом потоке запущен неподконтрольный код, и если этот код будет ждать чего-то и использовать ту же блокировку, то возникнет состояние взаимоблокировки.

Одно из решений этой проблемы — перемещение вызова `TrySetResult` за пределы блока `lock`:

```c#
int copyOfValue;
lock(_valueLock)
{
    copyOfValue = _value;
}
_taskSource.TrySetResult(copyOfValue);
```

Другой вариант — заставить `TaskCompletionSource` запустить код в другом потоке. Это можно сделать с помощью конструктора `TaskCompletionSource`, который принимает параметр `TaskCreationOptions`, и передать ему значение `TaskCreationOptions.RunContinuationsAsynchronously`:

```c#
_taskSource = new TaskCompletionSource<int>(TaskCreationOptions.RunContinuationsAsynchronously);
```

Все сказанное здесь также относится и к другим методам, завершающим задачу (`SetResult`, `SetException`, `TrySetException`, `SetCanceled` и `TrySetCanceled`).

#### Пример: ожидание инициализации

```c#
public class RequiresInit
{
    private Task<int> _value;

    public RequiresInit ()
    {
        var tcs = new TaskCompletionSource<int>();
        // Присваивает задачу перед выходом из конструктора
        _value = tcs.Task;
        Task.Run(() =>
        {
            try
            {
                // Имитирует продолжительный процесс инициализации
                Thread.Sleep(1000);        
                // Устанавливает результат задачи
                tcs.TrySetResult(7);
            }
            catch(Exception ex)
            {
                tcs.TrySetException(ex);
            }
        });
    }

    public async Task<int> Add1()
    {
        // Ждет результата, если необходимо
        var actualValue = await _value;
        return actualValue+1;
    }
}
```

#### Пример: адаптация старых API

Наиболее простым применением `TaskCompletionSource` является адаптация асинхронных API, несовместимых с `await`.

```c#
public interface IAsyncOperation
{
    void StartCalculation();
    event Action<int> CalculationComplete;
}
```

```c#
public Task<int> CallAsyncOperation()
{
    var tcs = new TaskCompletionSource<int>();
    _asyncOperation.CalculationComplete += result => tcs.TrySetResult(result);
    _asyncOperation.StartCalculation();
    return tcs.Task;
}
```

#### Итоги главы

> - `TaskCompletionSource` можно использовать для создания объектов `Task`, а `TaskCompletionSource<T>` — для создания объектов `Task<T>`.
> - `TaskCompletionSource<T>.TrySetResult` завершает `Task<T>` с признаком успеха и устанавливает свойство `Result`.
> - `TaskCompletionSource.TrySetResult` завершает `Task` с признаком успеха, но не устанавливает результат, потому что `Task` не имеет результата.
> - `TaskCompletionSource<T>.TrySetException` и `TaskCompletionSource.Try­SetException` завершают задачу `Task`, записывают в ее свойство `Status` значение `Faulted` и сохраняют одно или несколько исключений в `Task<T>` или `Task`.
> - `TaskCompletionSource<T>.TrySetCanceled` и `TaskCompletionSource.TrySetCanceled` завершают задачу `Task` и записывают в ее свойство `Status` значение `Canceled`.
> - При использовании `await`, вызове `Wait` или чтении свойства `Result` отмененной задачи `Task` выбрасывается исключение `TaskCanceledException`. Свойство `Exception` получит значение `null`. Проверить, была ли задача отменена, в этом случае можно с помощью свойства `Status` или свойства `IsCanceled`.
> - Все методы `TrySetXXX`, упомянутые ранее, вернут значение `true`, если задача `Task` завершилась, и `false`, если задача уже была завершена к моменту вызова метода.
> - Есть также вариант `SetXXX`, который выбрасывает исключение, если задача `Task` уже завершена. Вариант `TrySetXXX` предпочтительнее, потому что старый `SetXXX` может вызвать состояние гонки в некоторых многопоточных сценариях.
> - По умолчанию, продолжения (код после `await` или в обратных вызовах `ContinueWith`) могут запускаться немедленно внутри вызова `TrySetXXX` или `SetXXX`, что делает небезопасным их вызов при удержании блокировки. Чтобы запустить продолжение в другом потоке (и сделать безопасным его вызов при удержании блокировки), можно передать флаг `TaskCreationOptions.Run­ContinuationsAsynchronously` конструктору `TaskCompletionSource`.

#### Контексты синхронизации

`SynchronizationContext` — это универсальный способ запуска кода в другом потоке.

```c#
using System.Collections.Concurrent;

public class SingleThreadSyncContext : SynchronizationContext
{
    public static void Run(Func<Task> startup)
    {
        var prev = SynchronizationContext.Current;
        try
        {
            var ctxt = new SingleThreadSyncContext();
            // Свяжет SynchronizationContext с потоком
            SynchronizationContext.SetSynchronizationContext(ctxt);
            // Запускает очередь заданий
            ctxt.Loop(startup);
        }
        finally
        {
            // Восстанавливает оригинальный SynchronizationContext
            SynchronizationContext.SetSynchronizationContext(prev);
        }
    }

    private BlockingCollection<(SendOrPostCallback call,object? state)> _queue = new();

    private void Loop(Func<Task> startup)
    {
        // Прекращает работу после завершения первого метода
        startup().ContinueWith(t => _queue.CompleteAdding());
        // Цикл очереди заданий
        foreach(var next in _queue.GetConsumingEnumerable())
        {
            next.call(next.state);
        }
    }

    public override void Post(SendOrPostCallback d, object? state)
    {
        _queue.Add((d, state));
    }

    public override void Send(SendOrPostCallback d, object? state)
    {
        // не используется инструкциями async/await
        throw new NotImplementedException();
    }

    public override SynchronizationContext CreateCopy()
    {
        // не используется инструкциями async/await
        throw new NotImplementedException();
    }

    public override int Wait(IntPtr[] waitHandles, bool waitAll, int millisecondsTimeout)
    {
        // не используется инструкциями async/await
        throw new NotImplementedException();
    }        
}
```

Код выводит идентификатор текущего потока, вызывает `await`, а затем снова выводит идентификатор текущего потока:

```c#
    Console.WriteLine($"перед await {Thread.CurrentThread.ManagedThreadId}");
    await Task.Delay(500);
    Console.WriteLine($"после await {Thread.CurrentThread.ManagedThreadId}");
```

#### Переключение потоков — ConfigureAwait(false)

Если запустить эту программу как консольное приложение, то можно увидеть, что при вызове `await` без `ConfigureAwait(false)` она переключит потоки. Причина в том, что, пока `await` пытается оставаться в том же `SynchronizationContext` (не в потоке), у программы нет другого потока, и `await` продолжит выполнение в пуле потоков.

```c#
    Console.WriteLine($"1: {Thread.CurrentThread.ManagedThreadId}");
    await Task.Delay(500);
    Console.WriteLine($"2: {Thread.CurrentThread.ManagedThreadId}");
```

В следующем примере использование `ConfigureAwait(false)` не привело к переключению потоков. Так получилось, потому что `DoSomething` всегда возвращает завершенную задачу, а применение `await` к завершенной задаче просто продолжает работу в том же потоке.

```c#
Console.WriteLine($"1: {Thread.CurrentThread.ManagedThreadId}");
await DoSomething().ConfigureAwait(false);
Console.WriteLine($"2: {Thread.CurrentThread.ManagedThreadId}");

async Task DoSomething()
{
    Console.WriteLine("что-то выполнилось");
}
```

`ConfigureAwait(false)` можно использовать для предотвращения взаимоблокировок, однако лучший способ - если не смешивать асинхронные и блокирующие операции и просто использовать `await`, то проблемы и не возникнет:

```c#
private async void button1_Click(object sender, EventArgs ea)
{
    // Использована инструкция await
    var result = await DoSomething();
    label1.Text = result;
}

private async Task<string> DoSomething()
{
    await Task.Delay(500);
    return "выполнено";
}
```

Вызов `ConfigureAwait(false)` может быть полезен в случаях, когда неизвестно, является вызывающий код асинхронным, или блокирующим, что типично для случаев, когда пишется библиотека.

#### Дополнительные параметры ConfigureAwait

Несмотря на определенную полезность в особых случаях, дополнительные параметры влекут за собой неочевидные сложности, поэтому не рекомендуется использовать их в обычных приложениях.

#### Task.Yield: возможность выполнить другой код

Внутри системы события, генерируемые Windows (движения мыши, нажатия клавиш клавиатуры и т. д.), задания, добавленные с помощью `Control.Begin­Invoke` и `SynchronizationContext`, хранятся в так называемой очереди ввода (потому что ее основная функция — передача ввода из пользовательского интерфейса в приложение).

Когда вызов `Task.Yield()` с помощью `await` выполняется в потоке пользовательского интерфейса, то код после `await` добавляется в конец входной очереди и выполняется после всех других событий, которые уже ожидают обработки.

```c#
private async void button1_Click(object sender, EventArgs ea)
{
    int i=0;
    while(true)
    {
        label1.Text = (++i).ToString();
        await Task.Yield();
    }
}
```

#### Планировщики задач

`async`/`await` имеют собственную инфраструктуру принятия решения о выборе потока для запуска кода. Эта инфраструктура основана на классе `TaskScheduler`. Классы, производные от `TaskScheduler`, как и классы, производные от `SyncronizationContext`, знают, как получить задачу, созданную `await`, и запланировать ее выполнение в некотором потоке когда-нибудь в будущем.

Планировщик задач по умолчанию (доступный через статическое свойство `TaskScheduler`.Default) всегда ставит код в очередь для выполнения в пуле потоков.

В отличие от `SynchronizationContext`, текущий `TaskSchuduler` установить нельзя, но можно установить планировщик задач при вызове `Task.Run`, `ContinueWith` или при использовании для запуска кода любого другого способа, совместимого с `async`/`await`.

В примере ниже `TaskScheduler` передается через необязательный параметр. Планировщик создан из текущего `SynchronizationContext`, поэтому лямбда-функция будет работать в текущем потоке.

```c#
Task.Delay(500).ContinueWith(t => Console.WriteLine("Привет"),
    TaskScheduler.FromCurrentSynchronizationContext());
```

Как и в случае с `SyncronizationContext`, вызов `ConfigureAwait(false)` заставит `await` игнорировать текущий `TaskScheduler` и использовать планировщик по умолчанию.

#### Итоги главы

> - Вот упрощенные правила выбора потока для запуска кода после `await`:
>     - в приложениях с графическим интерфейсом (WinForms и WPF), если `await` вызывается в потоке пользовательского интерфейса и отсутствует вызов `ConfigureAwait(false)`, то код после `await` будет выполняться в том же потоке;
>     - в ASP.NET Classic (Framework 4.8 и младше), если `await` вызывается в потоке, обрабатывающем веб-запрос, и отсутствует вызов `ConfigureAwait(false)`, то код после `await` будет выполняться в том же потоке;
>     - во всех остальных случаях код после `await` будет выполняться в пуле потоков.
> - Однако фактически применяются следующие правила:
>     - если задача уже завершилась и не используется `ConfigureAwait`(`Configure­AwaitOptions.ForceYielding`), то код продолжит выполняться немедленно в том же потоке, `ConfigureAwait(false)` в этом случае не дает никакого эффекта;
>     - если в текущем потоке установлен `SynchronizationContext` и отсутствует вызов `ConfigureAwait(false)`, то будет использоваться `SynchronizationContext`;
>     - если с текущей задачей связан `TaskScheduler` и отсутствует вызов `ConfigureAwait(false)`, то будет использоваться `TaskScheduler`;
>     - если имеется вызов `ConfigureAwait(false)` или поток не имеет `Synchro­nizationContext` и `TaskScheduler`, то будет использоваться планировщик задач по умолчанию, а код продолжит выполнение в пуле потоков.
> - Если не используются сторонние фреймворки и не реализован собственный класс `SynchronizationContext` или `TaskScheduler`, то эти два набора правил дадут одинаковые результаты.
> - `ConfigureAwait(false)` заставляет `await` игнорировать текущий `Synchro­nizationContext` или `TaskScheduler`. Такое поведение помогает предотвратить взаимоблокировки, но может сделать использование `await` гораздо менее удобным.
> - Правила использования `ConfigureAwait(false)`:
>     - при разработке приложения не следует использовать `ConfigureAwait(false)`. Поведение по умолчанию существует не просто так;
>     - если код должен продолжить выполнение в том же потоке, например, при изменении настроек потока или при использовании локального хранилища, то не следует использовать `ConfigureAwait(false)`;
>     - если код предназначен для работы в средах, не использующих `SynchronizationContext` (например, в консольных приложениях и в ASP.NET Core), то не следует использовать `ConfigureAwait(false)`;
>     - при написании библиотечного кода, когда контекст выполнения неважен, следует использовать `ConfigureAwait(false)` для каждого вызова `await`;
>     - при необходимости покинуть текущий контекст следует использовать `Task.Run` вместо `ConfigureAwait(false)`, потому что `ConfigureAwait(false)` ничего не делает, если задача уже завершилась.

### Глава 12. async/await и исключения

В простом синхронном коде исключения всплывают вверх по стеку вызовов. Но в асинхронном коде постоянно происходит регистрация обратных вызовов для последующего вызова, часто в других потоках, поэтому стек вызовов больше не описывает поток выполнения кода.

#### Исключения и асинхронный код

Пример кода:

```c#
public async Task<int> MyMethod()
{
    await File.ReadAllBytesAsync("file.bin");
    throw new NotImplementedException();
}
```

И как его преобразует компилятор:

```c#
public async Task<int> MyMethod()
{
    var result = new TaskCompletionSource<int>();
    File.ReadAllBytesAsync("file.bin").ContinueWith(t=>
    {
        try
        {
            throw new NotImplementedException();
        }
        catch(Exception ex)
        {
            result.TrySetException(newAggregateException(ex));
        }
    });

    return result.Task;
}
```

Здесь компилятор добавил блок try внутри продолжения (код, который передается в `ContinueWith`). Если ошибка возникнет до первого вызова `await`, то метод выбросит исключение как обычно. А если ошибка возникнет после первого вызова `await`, то исключение будет перехвачено кодом, который сгенерировал компилятор, и сохранено в возвращаемой задаче `Task`. Именно так работает бо́льшая часть асинхронного кода: асинхронный метод может выбрасывать исключение как обычно, а также сообщать об ошибке с помощью объекта `Task` (посредством значения `Faulted` в свойстве `Status` задачи `Task` и самого исключения в свойстве `Task`.`Exception`).

Если `await` задействуется при вызове метода, то обе ситуации выглядят одинаково. Но если `await` не используется (например, если собираются несколько задач и используется `Task.WhenAny` или `Task.WhenAll`), то необходимо обрабатывать и исключения, выбрасываемые асинхронными методами, и исключения, хранящиеся в возвращаемом объекте `Task`.

#### await и AggregateException

Свойство `Task.Exception` всегда хранит `AggregateException`. `Task` использует `AggregateException`, чтобы иметь возможность представлять результат нескольких операций, выполняемых параллельно (например, нескольких асинхронных операций, переданных в `Task.WhenAll`). Неудачей могут завершиться несколько фоновых операций, поэтому и нужен способ хранения более чем одного исключения.

На практике эта функция почти никогда не применяется. Фактически она встречается настолько редко, что если при использовании `await` задача `Task` потерпела неудачу, то `await` всегда будет повторно выбрасывать первое исключение из `AggregateException`, а не само исключение `AggregateException`, остальные исключения будут проигнорированы.

#### Потеря исключений

Компилятор генерирует код для перехвата исключений и прячет их внутри `Task`, а `await` повторно выбрасывает это исключение. Но если код не использует `await` произойдет потеря исключения. Код, сгенерированный компилятором, перехватит исключение, сохранит его в `Task`, и если прикладной код не прочитает исключение из `Task` (используя `await` или через свойство `Task`.`Exception`), то исключение будет проигнорировано.

#### Исключения и методы async void

Методы с возвращаемым значением типа `async void` не возвращают `Task`. Поскольку объект `Task`, в котором можно было бы сохранить исключение, отсутствует, компилятор не знает, как поступить с исключением, сгенерированным внутри метода, и поэтому не генерирует блок `try-catch`. В результате любое исключение поднимется по стеку вызовов в контекст `SynchronizationContext`, который запустил код. Поэтому всегда необходимо самостоятельно обрабатывать все исключения в методах `async void` и никогда не позволять исключениям выходить за их пределы.

#### Итоги главы

> - Исключения используют стек вызовов для поиска соответствующей инструкции catch, которую можно выполнить в случае ошибки, что является проблемой для асинхронного кода, потому что продолжения выполняются не в том же стеке вызовов, что и код, вызывающий асинхронный метод.
> - При использовании `async`/`await` компилятор генерирует код, похожий на синхронный. Код перехватывает исключение и сохраняет его в `Task`, `await` выбрасывает исключение внутри продолжения, создав иллюзию, что оно сгенерировано инструкцией `await`.
> - Каждый асинхронный метод может выбросить обычное исключение или сообщить о сбое, используя возвращаемую задачу `Task`. Применение `await` стирает различия между этими двумя режимами сбоя. Если `await` не используется, то оба случая необходимо обрабатывать самостоятельно.
> - Для хранения исключений внутри `Task` используется класс `AggregateExcep­tion` на тот случай, если `Task` представляет несколько асинхронных операций. Инструкция `await` игнорирует все исключения внутри `AggregateException`, кроме первого. Если не используется `await`, то необходимо обработать эту ситуацию самостоятельно, анализируя `Task.Exception`.
> - При игнорировании задачи `Task`, которая возвращается асинхронным методом (например, забыто ключевое слово `await`), исключения теряются.
> - Как следствие, если в коде происходит сбой и при этом не возникает исключения, то высока вероятность, что где-то забыто ключевое слово `await`.
> - Поддержка исключений, предлагаемая инструкциями `async`/`await`, основана на возвращемой задаче `Task`. Методы `async void` не возвращают задачу `Task` и поэтому лишены этой поддержки. Никогда не следует выбрасывать исключения в методах `async void` и нельзя допускать исключениям всплывать в этих методах.

### Глава 13. Потокобезопасные коллекции

#### Проблемы использования обычных коллекций

Коллекции `System.Collections.Generic` поддерживают множественное параллельное чтение, но могут быть повреждены и, как следствие, могут возвращать неожиданные результаты в случае одновременной записи из нескольких потоков или когда одни потоки их читают, а другие записывают. Кроме того, согласно официальной документации, итерации по коллекциям изначально не являются потокобезопасными, поэтому, приступая к итерациям по коллекции с помощью оператора цикла, такого как `foreach`, или Linq-выражения, необходимо предотвратить любые возможности записи в эти коллекции из других потоков на протяжении всего цикла.

Пример непотокобезопасного кода с блокировкой:

```c#
Item item;
lock(_dictLock)
{
    if(!dictionary.TryGetValue(itemId, out item))
    {
        item = CreateAndInitializeItem(itemId);
        // возникнет исключения, если несколько потоков пройдут проверку пока элемент не создан
        dictionary.Add(itemId,item);
    }
}
```

Кроме дополнительной проверки, здесь необходимо использовать оператор `[]`, который добавляет новый элемент в словарь - если указанный ключ отсутствует, и перезаписывает значение, если элемент с таким ключом уже существует. Этот прием решает проблему с исключением, но вносит новую малозаметную ошибку. Первый поток использует свою копию объекта Item, а второй и последующие потоки — копию, созданную вторым потоком. Если объект Item является неизменяемым, а инициализация всегда возвращает эквивалентный объект для одного и того же ключа, то такое решение допустимо. Иначе данные первого потока будут потеряны.

```c#
Item item;
bool exists;

lock(_dictLock)
{
    exists = dictionary.TryGetValue(itemId, out item);
}
if(!exists)
{
    item = CreateAndInitializeItem(itemId);
    // Снова устанавливается блокировка и коллекция проверяется на наличие элемента
    lock(_dictLock)
    {
        if(dictionary.TryGetValue(itemId, out var itemFromOtherThread))
        {
            item = itemFromOtherThread;
        }
        else
        {
            dictionary.Add(itemId,item);
        }
    }
}
```

#### Потокобезопасные коллекции

Коллекции `System.Collections.Concurrent` используют специализированные стратегии блокировки и приемы выполнения операций без блокировки, чтобы оставаться потокобезопасными.

##### ConcurrentDictionary&lt;TKey,TValue&gt;

`ConcurrentDictionary<TKey,TValue>` — это потокобезопасная альтернатива для `Dictionary<TKey,TValue>`.

В многопоточном коде всегда есть вероятность, что другой поток добавит элемент прямо перед тем, как текущий поток вызовет `Add` и тем самым выбросит исключение. По этой причине метод `Add` в `ConcurrentDictio­nary<TKey,TValue>` был заменен методом `TryAdd`.

На самом деле правильнее иметь возможность объединить `TryGetValue` и `TryAdd` в одну атомарную операцию, для устранения этой проблемы. Concurrent­`Dictionary<TKey,TValue>` дает такую возможность в виде метода `GetOrAdd`, которая принимает значение словаря и делегат создания элемента.

```c#
var item = dictionary.GetOrAdd(itemId,CreateAndInitializeItem);
```

Класс `ConcurrentDictionary<TKey,TValue>` также имеет метод `TryRemove`, который удалит ключ со значением и вернет true, если ключ существовал. Если ключ отсутствовал, то вернет false.

Метод `TryUpdate` решает проблему, когда один поток может перезаписать данные, внесенные другим потоком.

```c#
private ConcurrentDictionary<string, int> _dictionary = new();
public void Increment(string key)
{
    // цикл повторяется пока не произойдет успешное обновление счетчика
    while(true)
    {
        int prevValue = _dictionary[key];
        if(_dictionary.TryUpdate(key, prevValue+1, prevValue))
            break;
    }
}
```

`ConcurrentDictionary<TKey,TValue>` не имеет асинхронных интерфейсов, но блокирует выполнение на очень короткое время и отлично работает в асинхронном коде.

##### BlockingCollection&lt;T&gt;

В роли базовой коллекции для `BlockingCollection<T>` можно использовать `ConcurrentQueue<T>`, `ConcurrentStack<T>` и `ConcurrentBag<T>`.

По умолчанию и чаще других используется `ConcurrentQueue<T>`. Коллекция `BlockingCollection<T>`, основанная на `ConcurrentQueue<T>`, сохраняет порядок элементов как в обычной очереди.

Коллекция `BlockingCollection<T>`, основанная на `ConcurrentStack<T>`, действует подобно стеку.

`ConcurrentBag<T>`, используется очень редко. `ConcurrentBag<T>` - это специализированная коллекция, оптимизированная для сценариев, когда один и тот же поток и читает значения из коллекции, и записывает их в нее.

`BlockingCollection<T>` также позволяет указать максимальный размер коллекции, что может пригодиться в случаях, когда скорость работы производителя намного превышает скорость работы потребителя. Эта возможность называется ограниченной емкостью (*bounded capacity*). Ограниченная емкость, в основном реализуется методом `Add`. Если коллекция достигла максимальной емкости, метод блокируется до тех пор, пока какой-то другой поток не извлечет элемент из коллекции. Метод `TryAdd` работает аналогично, но добавляет тайм-аут (который может быть равен нулю).

Метод Take возвращает следующий элемент из коллекции и удаляет его в одной потокобезопасной операции. Если коллекция пуста, то вызов Take будет блокироваться, пока другой поток не добавит элемент вызовом `Add` или `TryAdd`. `TryTake` работает аналогично Take, но с добавлением тайм-аута.

Наиболее распространенный способ чтения данных из `BlockingCollection<T>` - это цикл `foreach` в сочетании с вызовом метода `GetConsumingEnumerable`. Метод возвращает экземпляр `IEnumerable<T>`, который при использовании с `foreach` извлекает из коллекции текущий элемент в каждой итерации и, если коллекция пуста, блокируется до тех пор, пока другой поток не добавит элемент в коллекцию.

Возможность сообщить, что новых элементов больше не будет и можно выйти из цикла реализует `CompleteAdding`.

`BlockingCollection<T>` также содержит статические методы `AddToAny`, `Try­AddToAny`, `TakeFromAny` и `TryTakeFromAny`. В отличии от нестатических аналогов методы принимают массив коллекций `BlockingCollection<T>` и используют одну из них в зависимости от количества элементов в каждой коллекции. Недостаток - `AddToAny` и `TryAddToAny` никак не балансируют нагрузку. Они оптимизированы для максимально быстрого выполнения операции `AddToAny`, поэтому всегда будут искать самый быстрый вариант добавления элемента в коллекцию.

`BlockingCollection<T>` очень полезна при управлении собственными потоками, но, как следует из названия, она использует блокирующие операции и потому не соответствует модели асинхронного программирования.

```c#
BlockingCollection<int> blockingCollection = new BlockingCollection<int>();
Thread[] workers = new Thread[10];

// Создает 10 обрабатывающих потоков
for(int i=0; i<workers.Length; i++)
{
    workers[i] = new Thread(threadNumber =>
    {
        var rng = new Random((int)threadNumber);
        int count = 0;
        foreach (var currentValue in blockingCollection.GetConsumingEnumerable())
        {
            Console.WriteLine($"поток {threadNumber} значение {currentValue}");
            Thread.Sleep(rng.Next(500));
            count++;
        }
        Console.WriteLine($"поток {threadNumber}, всего {count} элементов");
    });
    workers[i].Start(i);
}

// Добавляет 100 элементов для обработки
for(int i=0;i<100;i++)
{
    blockingCollection.Add(i);
}

// Уведомляет, что элементов больше не будет
blockingCollection.CompleteAdding();
// Ожидает завершения всех потоков
foreach (var curentThread in workers)
    curentThread.Join();
```

##### Асинхронные альтернативы BlockingCollection

По состоянию на .NET версии 8 стандартная библиотека .NET не имеет асинхронных коллекций в целом и асинхронной версии `BlockingCollection<T>` в частности. Однако имеет несколько других классов, которые можно превратить в асинхронную очередь. Один из них — `Channel<T>`, потокобезопасная очередь с несколькими производителями и потребителями, разработанная для связи между программными компонентами.

`Channel<T>` — это коммуникационный канал. У каждого канала есть писатель, который может добавлять сообщения, и читатель, который может извлекать сообщения из канала. Канал сохраняет порядок сообщений, что делает его эквивалентом очереди.

```c#
var ch = Channel.CreateUnbounded<int>();
Task[] tasks = new Task[10];

// Запускает 10 асинхронных задач
for(int i=0; i<10;++i)
{
    var threadNumber = i;
    tasks[i] = Task.Run(async () =>
    {
        var rng = new Random((int)threadNumber);
        int count = 0;
        while (true)
        {
            // Ждет появления следующего элемента данных
            try
            {
                var currentValue = await ch.Reader.ReadAsync();
                
                Console.WriteLine($"задача {threadNumber} значение {currentValue}");
                Thread.Sleep(rng.Next(500));
                count++;
            }
            // Это исключение означает, что данных больше не будет
            catch(ChannelClosedException)
            {
                break;
            }
        }
        Console.WriteLine($"задача {threadNumber}, всего {count} элементов");
    });
}

// Добавляет 100 элементов для обработки
for (int i = 0; i < 100; i++)
{
    await ch.Writer.WriteAsync(i);
}

// Сообщает, что данных больше не будет
ch.Writer.Complete();
// Ждет завершения всех задач
Task.WaitAll(tasks);
```

##### ConcurrentQueue&lt;T&gt; и ConcurrentStack&lt;T&gt;

`ConcurrentQueue<T>` — это потокобезопасная версия `Queue<T>`, а `ConcurrentStack<T>` — потокобезопасная версия `Stack<T>`.

```c#
var queue = new ConcurrentQueue<int>();
// ....
// Проверяет и одновременно извлекает элемент
if(queue.TryDequeue(out var next))
{
    // использовать next
}
```

Классы `ConcurrentQueue<T>` и `ConcurrentStack<T>` можно использовать напрямую, но чаще они применяются в сочетании с `BlockingCollection<T>`.

##### ConcurrentBag&lt;T&gt;

Структура данных `ConcurrentBag<T>` не располагает элементы в каком-то определенном порядке — они могут извлекаться в любом порядке. `ConcurrentBag<T>` может хранить повторяющиеся элементы. Для добавления элементов `ConcurrentBag<T>` предлагает метод `Add`, а для извлечения — метод `TryTake`.

Реализация `ConcurrentBag<T>` использует отдельные очереди для каждого потока, а `TryTake` пытается возвращать элементы, добавленные тем же потоком. Это удобно тем, что `ConcurrentBag<T>` не должен блокироваться, если два потока одновременно попытаются получить элемент. Если элемент, добавленный текущим потоком, недоступен, то `TryTake` извлечет элемент из очереди другого потока (это называется перехватом работы — *work stealing*), но такая ситуация требует синхронизации потоков, что увеличивает накладные расходы и замедляет быстродействие. По этой причине `ConcurrentBag<T>` следует использовать, только если один и тот же поток (или набор потоков) и добавляет и извлекает элементы из коллекции.

Кроме того, `ConcurrentBag<T>` не следует использовать в асинхронном коде, потому что обычно отсутствует контроль над тем, какой поток обрабатывает коллекцию.

##### Когда следует использовать потокобезопасные коллекции

`ConcurrentDictionary<TKey,TValue>` - потокобезопасная альтернатива `Dictionary<TKey,TValue>`, `ConcurrentQueue<T>` и `ConcurrentStack<T>` - потокобезопасные реализации очереди и стека. Если нужен механизм блокировки потребителя при отсутствии элементов, то необходимо использовать `BlockingCollection<T>`. Однако `BlockingCollection<T>`, особенно его методы `Take` и `GetConsumingEnumerable`, не подходят для асинхронной модели программирования.

##### Когда не следует использовать потокобезопасные коллекции

Если есть необходимости использовать блокировку, чтобы сделать код потокобезопасным (не только для защиты доступа к коллекции), то лучше использовать эту блокировку и для синхронизации доступа и к коду и к коллекции, в этом случае потокобезопасная коллекция не нужна. Код, использующий непотокобезопасные альтернативы (`Dictionary<TKey,TValue>`, `Queue<T>` и `Stack<T>`), получится проще и быстрее.

Если потокобезопасность нужна только из-за того, что коллекция передается какому-то (возможно, внешнему) коду, который не изменяет коллекцию и допускает, что данные коллекции могли немного устареть, следует рассмотреть возможность использовать неизменяемые коллекции.

#### Неизменяемые коллекции

Проблемы потокобезопасности всегда сводятся к тому, что несколько потоков изменяют данные одновременно: одни потоки читают данные, в то время как другие их изменяют, или к проблемам с временем выполнения, из-за которых потоки изменяют данные в неправильном порядке. Если данные никогда не изменяются, то ни одна из этих проблем не возникнет и код по своей природе будет потокобезопасным.

Если стандартные коллекции основаны на массивах (т.к. доступ в них выполняется быстрее), то в неизменяемых коллекциях при запросе возвращается новая копия коллекции - поддерживать несколько активных копий коллекции эффективнее на списках.

Все неизменяемые коллекции используют одну и ту же базовую тактику — размещение данных внутри узловых объектов и проектирование операций таким образом, чтобы каждая «модифицированная» копия могла использовать большинство узлов предыдущей коллекции.

Особенность использования неизменяемых коллекций заключается в том, что ссылка на неизменяемую коллекцию сохраняется в обычной переменной, что может привести к ошибкам в многопоточном коде:

```c#
public class InventoryManager
{
    private ImmutableDictionary<string,int> _bookIdToQuantity;

    public bool TryToBuyBook(string bookId)
    {
        // Получает предыдущее количество
        if(!_bookIdToQuantity.TryGetValue(bookId, out var copiesInStock))
            return false;

        if(copiesInStock == 0)
            return false;

        // Устанавливает новое количество
        _bookIdToQuantity = _bookIdToQuantity.SetItem(bookId, copiesInStock-1);
        return true;
    }
}
```

Возможные решения - `lock` плюс `Dictionary<TKey, TValue>`, использование потокобезапасной коллекции, использование `ImmutableInterlocked`.

##### ImmutableInterlocked

Класс `ImmutableInterlocked` позволяет выполнять операции изменения переменной, ссылающейся на неизменяемую коллекцию, без блокировок.

Например, для `ImmutableDictionary<TKey,TValue>` класс `ImmutableInterlocked` предоставляет методы `AddOrUpdate`, `GetOrAdd`, `TryAdd`, `TryRemove` и `TryUpdate`, которые аналогичны одноименным методам в `ConcurrentDictionary<TKey,TValue>`.

`ImmutableInterlocked.TryUpdate` делает то же самое для неизменяемых словарей: проверяет, было ли значение, которое мы пытаемся обновить, изменено кем-то другим. Если значение не изменилось, он заменит весь словарь новым словарем с одним измененным значением. Если значение было изменено другим потоком, то он так же, как `ConcurrentDictionary<TKey,TValue>.TryUpdate`, вернет `false`, ничего не изменив.

```c#
private ImmutalbeDictionаry<string,int> _bookIdToQuantity = new();

public bool TryToBuyBook(string bookId)
{
    while(true)
    {
        // Получает предыдущее количество 
        if(!_bookIdToQuantity.TryGetValue(bookId, out var copiesInStock))
            return false;
        if(copiesInStock == 0)
            return false;
        // Устанавливает новое количество, только если оно не было изменено другим потоком
        if(ImmutableInterlocked.TryUpdate(ref _bookIdToQuantity, bookId, copiesInStock-1, copiesInStock))
            // Возвращает true в случае успеха
            return true;
        // Если значение изменено другим потоком, повторяет попытку
    }
}
```

`ImmutableInterlocked` также предоставляет методы `Push` и `TryPop` для использования с `ImmutableStack<T>`, а также `Enqueue` и `TryDequeue` для `ImmutableQueue<T>`.

`ImmutableInterlocked` — операция безопасна, только если все изменения производятся с помощью `ImmutableInterlocked`.

Кроме того нельзя использовать `ImmutableInterlocked` для потокобезопасного обновления нескольких коллекций одновременно. Если, например, нужно добавить один и тот же ключ в два словаря, то этого не получится сделать с помощью `ImmutableInterlocked`, не создав временное окно, в течение которого другой поток сможет прочитать изменение в первом словаре до обновления второго.

##### ImmutableDictionary&lt;TKey,TValue&gt;

`ImmutableDictionary<TKey,TValue>` — это неизменяемая версия `Dictionary<TKey,TValue>`.

`ImmutableDictionary<TKey,TValue>` позволяет проверить наличие ключа (`ContainsKey`), извлечь значение (оператор `[]`) с помощью оператора `[]` и выполнить оба действия атомарно с помощью `TryGetValue`.

Чтобы изменить определенное значение внутри словаря, нужно вместо оператора `[]` использовать метод `UpdateValue`, потому что оператор `[]` не имеет возможности вернуть новый словарь.

При необходимости внести несколько изменений разных типов (например, добавить одно значение и удалить другое) или алгоритм не позволяет сгруппировать изменения (например, если нет возможности заменить несколько вызовов `Add` одним вызовом `AddRange`), то можно воспользоваться объектом-­построителем (*builder*). Объект-построитель создается с помощью метода `ToBuilder` словаря.

После выполнения необходимых изменений, следует вызвать метод `ToImmutable` построителя, который создаст новый `ImmutableDictionary<TKey, TValue>` со всеми изменениями.

Построитель не является ни неизменяемым, ни потокобезопасным и позволяет быстро и эффективно создавать новые объекты `ImmutableDictio­nary<TKey,TValue>`, но он не предоставляет никаких средств для работы в многопоточной среде.

##### ImmutableHashSet&lt;T&gt; и ImmutableSortedSet&lt;T&gt;

`ImmutableHashSet<T>` и `ImmutableSortedSet<T>` - неизменяемые версии `HashSet<T>` и `SortedSet<T>`. Оба класса представляют множества — коллекции, которые могут содержать ноль или более элементов без дубликатов и поддерживают операции из теории множеств (Except, Intersect, IsSubsetOf, IsSupersetOf и др.).

По аналогии с другими неизменяемыми коллекциями все методы, изменяю­щие коллекцию, возвращают новую коллекцию с внесенными изменениями. Содержат метод `ToBuilder`, возвращающий объект-построитель.

##### ImmutableList&lt;T&gt;

`ImmutableList<T>` - неизменяемая версия `List<T>`. Все методы, изменяющие список, возвращают новый `ImmutableList<T>`. Содержит метод `ToBuilder`, возвращающий объект-построитель.

Если есть переменная, содержащая объект `ImmutableList<T>`, к которой обращаются разные потоки, то синхронизировать доступ к ней необходимо самостоятельно. `ImmutableInterlocked` не поддерживает `ImmutableList<T>`.

##### ImmutableQueue&lt;T&gt; и ImmutableStack&lt;T&gt;

`ImmutableQueue<T>` и `ImmutableStack<T>` - неизменяемые версии `Queue<T>` и `Stack<T>`. Обычно лучше отдать предпочтение `ConcurrentQueue<T>` и `ConcurrentStack<T>`, за исключением случаев, когда код пишется в функцио­нальном стиле.

##### ImmutableArray&lt;T&gt;

Все непотоко­безопасные коллекции используют массивы, потому что процессор работает с ними намного быстрее, но неизменяемые коллекции не используют массивы, потому что иначе пришлось бы копировать все данные при каждом изменении. `ImmutableArray<T>` - исключение, которое, как следует из названия, действительно использует массив, который копируется при каждом исключении.

`ImmutableInterlocked` поддерживает `ImmutableArray<T>`, предлагая методы InterlockedCompereExchange, InterlockedExchange и InterlockedInitilize, но их лучше не использовать. Они сложны, и работа с ними чревата ошибками. Намного проще использовать оператор `lock`.

В общем случае `ImmutableArray<T>` используется как замороженные коллекции. Он хорошо подходит для случаев, когда нужна последовательная коллекция (например, `List<T>` или массив), потокобезопасная и доступная только для чтения. Однако, поскольку повторное создание `ImmutableArray<T>` обходится слишком дорого, его следует использовать только тогда, когда он вообще не будет изменяться.

##### Когда использовать неизменяемые коллекции

Неизменяемые коллекции очень распространены в функциональном программировании.

Также удобны, когда нужно сохранить предыдущие состояния системы, например, для реализации возможности отмены. Важно, что неизменяемые коллекции не подходят для случаев, когда нужно сохранить состояние системы для целей аудита, потому что тогда состояние системы нужно сохранять на диске, а неизменяемые коллекции находятся только в памяти.

Неизменяемые коллекции также полезны, когда нужно передать коллекцию стороннему коду. В таком случае не придётся дублировать данные для защиты и отправлять копию стороннему коду.

Неизменяемые коллекции требуют учитывать, что, несмотря на полную потокобезопасность самих неизменяемых коллекций, «изменение коллекции» подразумевает создание новой коллекции, а вновь созданные копии обычно присваиваются той же переменной, что и предыдущая коллекция. Эта переменная будет изменяться с каждым изменением коллекции, поэтому доступ к ней следует синхронизировать, как и к любой другой переменной, к которой одновременно обращается несколько потоков.

#### Замороженные коллекции

Используются, если данные никогда не изменяются. Замороженные коллекции - это коллекции, доступные только для чтения и оптимизированные для чтения.

В настоящее время существуют только два типа замороженных коллекций - `FrozenDictionary<TKey,TValue>` и `FrozenSet<T>` - версии `Dictionary<TKey,TValue>` и `HashSet<T>`. При необходимости замороженной версии `List<T>`, используется `ImmutableArray<T>`. Замороженных очередей и стеков не существует, потому что в этом нет смысла.

Пример инициализации `FrozenSet`:

```c#
var data = new List<int> {1,2,3,4};
var set = data.ToFrozenSet();
```

Инициализация `FrozenDictionary`:

```c#
var numberNames = new Dictionary<int,string>
{
    {1, "one"},
    {2, "two"}
};
var frozenDict = numberNames.ToFrozenDictionary();
```

#### Итоги главы

> - Обычные коллекции из пространства имен `System.Collections.Generic` можно читать сразу из нескольких потоков.
> - Запись из нескольких потоков одновременно или запись из одного потока, когда другие потоки выполняют чтение, не допускается и может привести к получению неверных результатов и даже к повреждению коллекций.
> - Потокобезопасные коллекции из пространства имен `System.Collections.Con­current` полностью потокобезопасны и поддерживают одновременные чтение и запись из нескольких потоков.
> - Потокобезопасные версии `Dictionary<TKey,TValue>`, `Queue<T>` и `Stack<T>` - `ConcurrentDictionary<TKey,TValue>`, `ConcurrentQueue<T>` и `ConcurrentStack<T>` соответственно. Их интерфейс отличается от обычных коллекций — он объединяет часто используемые операции в одну, чтобы избежать состояния гонки.
> - Коллекция `ConcurrentBag<T>` полезна в случаях, когда порядок извлечения элементов не имеет значения. Она предназначена для использования, когда одни и те же потоки одновременно читают из коллекции и записывают в нее.
> - Класс `BlockingCollection<T>` добавляет поддержку сценариев «производитель — потребитель» и помогает ограничить размер коллекции. По умолчанию `BlockingCollection<T>` работает как очередь, но может также использоваться как стек.
> - Коллекции `ConcurrentDictionary<TKey,TValue>`, `ConcurrentQueue<T>`, `ConcurrentStack<T>` и `ConcurrentBag<T>` можно использовать в асинхронном коде.
> - Класс `BlockingCollection<T>`, как следует из названия, является блокирующим, поэтому следует использовать его с осторожностью (а лучше вообще не использовать) с асинхронным кодом.
> - `BlockingCollection<T>` не имеет асинхронной версии, зато есть класс `Channel<T>`, с помощью которого можно создать асинхронную версию наиболее распространенного варианта использования `BlockingCollection<T>`.
> - Неизменяемые коллекции из пространства имен `System.Collections.Immu­table` — это коллекции, которые нельзя изменить (каждое изменение оставляет коллекцию нетронутой и создает новую коллекцию). Они потоко­безопасны: поскольку по определению они вообще не могут быть изменены, они также не могут быть изменены другими потоками во время использования.
> - Если переменная, ссылающаяся на неизменяемую коллекцию, доступна нескольким потокам, то требуется синхронизировать доступ к переменной — в этом помогает `ImmutableInterlocked` (для словаря, очереди и стека).
> - Чтобы внести несколько изменений в неизменяемую коллекцию, используется метод `ToBuilder`. Он возвращает объект-построитель, который вносит изменения без создания новых коллекций, и затем, когда вызывается его метод `ToImmutable`, создает одну новую коллекцию сразу со всеми изменениями. Объект-построитель не является потокобезопасным.
> - Классы `ImmutableDictionary<TKey,TValue>`, `ImmutableHashSet<T>`, `Immutable­SortedSet<T>`, `ImmutableQueue<T>`, `ImmutableStack<T>` и `ImmutableList<T>` являются неизменяемыми версиями одноименных классов без префикса `Immutable`. Эти коллекции читаются медленнее обычных или потокобезопасных коллекций, зато их копии создаются быстро.
> - Коллекция `ImmutableArray<T>` — это неизменяемый массив. Он отличается самой высокой скоростью чтения среди всех неизменяемых коллекций, но самой низкой скоростью изменения (то есть создания измененной копии). Также поддерживает `ReadOnlyMemory<T>` и `ReadOnlySpan<T>`.
> - Замороженные коллекции оптимизированы для чтения.
> - Замороженные коллекции, как и неизменяемые, по своей природе потокобезопасны.
> - Существуют только две замороженные коллекции: `FrozenDictionary<TKey,TValue>` и `FrozenSet<T>`.
> - Обычно для создания замороженной коллекции сначала создается обычная коллекция, а затем к ней применяется метод `ToFrozenSet` или `ToFrozen­Dictionary`.

### Глава 14. Асинхронная генерация коллекций / await foreach и IAsyncEnumerable

Иногда бывает нужно использовать `foreach` для обхода последовательности элементов, генерируемых на лету или извлекаемых из внешнего источника без предварительного сохранения всего набора элементов в коллекцию.

#### Итерации по асинхронной коллекции

Ключевое слово `foreach` - синтаксический сахар, способ записи цикла `while`. Пример цикла `foreach` и как его обрабатывает компилятор в общем случае без оптимизаций:

```c#
// Цикл foreach
foreach([loop-variable-type] [loop-variable] in [collection])
{
    [loop-body]
}

// как его обрабатывает компилятор
using(var enumerator = [collection].GetEnumerator())
{
    while(enumerator.MoveNext())
    {
        [loop-variable-type] [loop-variable] = enumerator.Current;
        [loop-body];
    }
}
```

Для использования коллекции в асинхронном коде, когда извлечение следующего элемента производится в асинхронной операции, придется внести некоторые изменения в работу `foreach`. А именно, нужно добавить `await` в условие цикла `while` (третья строка в предыдущем фрагменте кода), а чтобы использовать `await`, метод `MoveNext` должен возвращать `Task<bool>` вместо `bool`. Именно это и делают инструкция `await` `foreach` и интерфейс `IAsyncEnumerable<T>`.

| `IEnumerable<T>` | `IAsyncEnumerable<T>` |
|---|---|
| `IEnumerator<T> GetEnumerator()` | `IAsyncEnumerator<T> GetAsyncEnumerator()` |

| `IEnumerator<T>` | `IAsyncEnumerator<T>` |
|---|---|
| `T Current {get;}` | `T Current {get;}` |
| `bool MoveNext()` | `ValueTask<bool> MoveNextAsync()` |
| `void Dispose()` | `ValueTask DisposeAsync()` |

```c#
// Цикл await foreach
await foreach([loop-variable-type] [loop-variable] in [collection])
{
    [loop-body]
}

// как его обрабатывает компилятор
await using(var enumerator = [collection].GetEnumerator())
{
    while(await enumerator.MoveNext())
    {
        [loop-variable-type] [loop-variable] = enumerator.Current;
        [loop-body];
    }
}
```

#### Создание асинхронной коллекции

Aсинхронных коллекций как таковых не существует — по крайней мере в стандартной библиотеке. Все коллекции, включенные в библиотеку .NET, хранят элементы в памяти, и нет никакой необходимости получать элементы (асинхронно или как-то иначе), которые уже хранятся в памяти.

Когда речи идет о поддержке асинхронных коллекций, то в действительности имеется в виду возможность использовать цикл `await foreach` для обработки последовательности элементов данных, которые генерируются или извлекаются асинхронно - фактически нужна асинхронная версия инструкции `yield return`.

```c#
// Вместо IEnumerable<int> используется async IAsyncEnumerable<int>
private async IAsyncEnumerable<int> AsyncYieldDemo()
{
    yield return 1;
    // Можно использовать await
    await Task.Delay(1000);
    yield return 2;
}

public async Task UseAsyncYieldDemo()
{
    // Вместо foreach используется await foreach
    await foreach(var current in AsyncYieldDemo())
    {
        Console.WriteLine($"Получил {current}");
    }
}
```

#### Отмена итерации по асинхронной коллекции

Асинхронные операции часто поддерживают возможность отмены, и хотелось бы иметь аналогичную возможность в операциях, вызываемых из циклов `await foreach`. Для поддержки этой возможности метод `GetAsyncEnumerator` принимает токен отмены в качестве необязательного параметра, но само по себе это не решает проблему, потому что:
- код, вызывающий `GetAsyncEnumerator`, при использовании `await foreach` генерируется компилятором и нет очевидного способа передать токен отмены;
- код `GetAsyncEnumerator` тоже генерируется компилятором и снова нет очевидного способа задать параметр метода.

Первая проблема решается методом-расширением `WithCancellation`. Этот метод можно вызвать для любого `IAsyncEnumerable<T>`, и он вернет новый объект, который тоже реализует интерфейс `IAsyncEnumerable<T>`.

```c#
await foreach(var item in collection.WithCancellation(token))
```

Чтобы решить проблему с передачей токена отмены в `GetAsyncEnumerator` необходимо подсказать компилятору, какой параметр использовать, сделать это можно с помощью атрибута `[EnumeratorCancellation]`.

```c#
// С помощью [EnumeratorCancellation] явно задается параметр для приема токена отмены
private async IAsyncEnumerable<int> AsyncYieldDemo([EnumeratorCancellation] CancellationToken cancellationToken = default)
{
    yield return 1;
    await Task.Delay(1000, cancellationToken);
    yield return 2;
}

public async Task UseAsyncYieldDemo()
{
    var cancel = new CancellationTokenSource();
    var collection = AsyncYieldDemo();

    // Отмена итерации в текущей реализации все равно выберет первый элемент 
    // cancel.Cancel();

    // Использует WithCancellation для передачи токена отмены
    await foreach(var current in collection.WithCancellation(cancel.Token))
    {
        Console.WriteLine($"Получил {current}");
    }
}
```

В данном примере вызов `cancel.Cancel` приведет к тому, что все равно отобразиться "Получил 1". `CancellationToken` - это всего лишь потокобезопасный флаг, который можно использовать для проверки необходимости отмены операции. В примере вообще не проверяется отмена в цикле, и в методе `AsyncYieldDemo` генерируется первое значение без проверки флага. Первая проверка происходит внутри вызова `Task.Delay`.

#### Другие варианты

В дополнение к методу `WithCancellation` есть метод `ToBlockingEnumerable`. Он заключает `IAsyncEnumerable<T>` в синхронный `IEnumerable<T>`, который можно использовать в обычном цикле `foreach` в синхронном коде.

Метод `ToBlockingEnumerable` позволяет использовать асинхронный API из синхронного кода. Это эквивалентно вызову `Wait()` для каждой задачи, возвращаемой методом `MoveNextAsync`.

Метод `ToBlockingEnumerable`, как и другие способы вызова `Wait()`, сводит на нет преимущества асинхронного программирования и в некоторых случаях может вызывать состояние взаимоблокировки. Его следует использовать, только когда асинхронная коллекция используется в синхронном коде и нет другого выбора.

#### IAsyncEnumerable&lt;T&gt; и LINQ

LINQ для `IAsyncEnumerable<T>` реализуется через набор расширений, которые позволяют писать запросы в стиле LINQ поверх асинхронных последовательностей. Основные идеи: использовать асинхронные потоки вместо синхронных и применять асинхронные версии операторов LINQ (`Where`, `Select`, `ToDictionaryAsync` и т.д.) через встроенные возможности .NET и асинхронные методы.

[Обзор и описание класса `AsyncEnumerable` (System.Linq) с набором методов для запросов к `IAsyncEnumerable`, включая ToDictionaryAsync и ToLookupAsync.](https://learn.microsoft.com/en-us/dotnet/api/system.linq.asyncenumerable?view=net-11.0)

#### Пример: итерации по данным, получаемым асинхронно

```c#
public class Async NumbersProcessor
{
    // Вместо IEnumerable<int> метод объявляется как async IAsyncEnumerable<int>
    private async IAsyncEnumerable<int> GetNumbers(Stream stream)
    {
        var buffer = new byte[4];
        // Вместо stream.Read используется await stream.ReadAsync
        while(await stream.ReadAsync(buffer, 0, 4) == 4)
        {
            var number = BitConverter.ToInt32(buffer);
            yield return number;
        }
    }

    // Вместо void метод объявляется как async Task
    public async Task ProcessStream(Stream stream)
    {
        // Вместо foreach используется await foreach
        await foreach(var number in GetNumbers(stream))
        {        
            Console.WriteLine(number);
        }
    }
}
```

Чтобы иметь возможность использовать `await`, нужно объявить метод асинхронным, а асинхронные методы не могут возвращать `IEnumerable<int>`, поэтому необходимо дополнительно поменять тип возвращаемого значения на `IAsyncEnumerable<int>`.

Также нужно заменить `foreach` на `await foreach`. Но `await foreach` можно использовать только в асинхронных методах, поэтому метод нужно объявить асинхронным и поменять тип возвращаемого значения с `void` на `Task`.

#### Пример: асинхронная очередь, подобная BlockingCollection&lt;T&gt;

```c#
public class ChannelAsyncCollection<T>
{
    private Channel<T> _channel = Channel.CreateUnbounded<T>();

    public void Add(T item)
    {
        _channel.Writer.TryWrite(item);
    }

    public void CompleteAdding()
    {
        _channel.Writer.Complete();
    }

    public async IAsyncEnumerable<T> GetAsyncConsumingEnumerable()
    {
        while (true)
        {
            T next;
            try
            {
                next = await _channel.Reader.ReadAsync();
            }
            // Определяет, когда следует завершить итерации
            catch (ChannelClosedException)
            {
                yield break;
            }
            // Инструкция yield return вынесена за пределы блок try, иначе код не скомпилируется
            yield return next;
        }
    }
}
```

```c#
ChannelAsyncCollection <int> asyncCollection = new ChannelAsyncCollection <int>();
Task[] workers = new Task[10];

// Создает 10 рабочих потоков
for(int i=0; i<workers.Length; i++)
{
    var threadNumber = i;
    workers[i] = Task.Run(async () =>
    {
        var rng = new Random((int)threadNumber);
        int count = 0;
        await foreach (var currentValue in asyncCollection.GetAsyncConsumingEnumerable())
        {
            Console.WriteLine($"поток {threadNumber} значение {currentValue}");
            Thread.Sleep(rng.Next(500));
            count++;
        }
        Console.WriteLine($"поток {threadNumber}, всего {count} элементов");
    });
}

// Добавляет 100 элементов для обработки
for(int i=0;i<100;i++)
{
    asyncCollection.Add(i);
}

// Сообщает, что элементов больше не будет
asyncCollection.CompleteAdding();
// Ждет завершения всех потоков
await Task.WhenAll(workers);
```

#### Итоги главы

> - Ключевые слова `yield return` и `yield break` можно использовать вместе с `async`/`await`. Для этого метод объявляется асинхронным и указывается тип возвращаемого значения `IAsyncEnumerable<T>` вместо `IEnumerable<T>`. После этого в методе, выполняющем итерации, можно использовать `await`.
> - `IAsyncEnumerable<T>` и `IAsyncEnumerator<T>` являются асинхронными, `async`/`await`-совместимыми версиями `IEnumerable<T>` и `IEnumerator<T>`.
> - Компилятор преобразует метод в класс, встретив инструкцию `yield return` и инструкцию `await`.
> - Для итераций по полученному объекту `IAsyncEnumerable<T>` вместо `foreach` следует использовать `await foreach`.
> - Конструкция `await foreach` похожа на обычную конструкцию `foreach`, за исключением того, что выполняет `await` в каждой итерации.
> - Итерации можно отменить с помощью метода расширения `WithCancellation`. Этот метод передает токен отмены в `IAsyncEnumerable<T>` (или, если `IAsyncEnumerable<T>` создан для инструкции `yield return`, то может передать его в метод, генерирующий последовательность). Токен отмены — это просто флаг, для остановки итераций должен иметься код, проверяющий статус токена и останавливающий итерирование.
> - Применение метода расширения `ConfigureAwait` к `IAsyncEnumerable<T>` работает как вызов `Task.ConfigureAwait` в каждой итерации. Плюсы и минусы `ConfigureAwait` обсуждались в главе 11.
> - Метод расширения `ToBlockingEnumerable` заключает `IAsyncEnumerable<T>` в `IEnumerable<T>`, который выполняет эквивалент вызова `Task.Wait` в каждой итерации. Как и `Task.Wait` , метод может вызывать проблемы с производительностью и взаимоблокировкой. Его следует использовать только для вызова асинхронных API из синхронного кода и только если API поддерживает этот вариант использования.
> - Асинхронные последовательности имеют встроенную поддержки LINQ, начиная с .NET 10 с помощью класса `AsyncEnumerable`, а также в более ранних версиях с помощью nuget-пакета "System.Linq.Async" от команды Rx.NET.
> - `yield return` и `await foreach` можно использовать в простом коде, который создает и обрабатывает последовательности асинхронно сгенерированных или полученных элементов данных.
> - `yield return` и `await foreach` также можно использовать для создания асинхронных очередей, заданий и другой многопоточной инфраструктуры.


## Приложение. Async Await Best Practices

### Саммари руководств по асинхронному программированию

|     Название      |                     Описание                      |           Исключения          |
|-------------------|---------------------------------------------------|-------------------------------|
| Избегать `async void` | Отдавать предпочтение асинхронным методам, возвращающим Task вместо void | Обработчики событий |
| Делать весь код асинхронным | Не смешивать блокирующий и асинхронный код | Main метод консольного приложения |
| ~~Конфигурация контекста~~ | ~~Использовать `ConfigureAwait(false)` где возможно~~ | ~~Методы, которые требуют контекст~~  |
| Конфигурация контекста | Избегать `ConfigureAwait(false)`, не смешивать асинхронные и блокирующие операции и просто использовать `await` | Методы библиотек, когда неизвестно является ли вызывающий код блокирующим или асинхронным |

*Примечание: использование `ConfigureAwait(false)` здесь противоречит рекомендациям Главы 11.*

### Асинхронный подход

|              Делать...              |    Вместо...     |       Используя...       |
|-------------------------------------|------------------|--------------------------|
| Получение результата фоновой задачи | `Task.Wait` или `Task.Result` | `await` |
| Ожидание завершения любой задачи | `Task.WaitAny` | `await Task.WhenAny` |
| Получение результатов множества задач | `Task.WaitAll` | `await Task.WhenAll` |
| Пауза | `Thread.Sleep` | `await Task.Delay` |

### Инструменты асинхронного программирования

Краткий справочник решения типовых задач асинхронного программирования.

|                     Задача                     |                                      Решение                                     |
|------------------------------------------------|-----------------------------------------------------------------------------------|
| Создание задачи для выполнения кода | `Task.Run` или `TaskFactory.StartNew` (не `Task` конструктор или `Task.Start`) |
| Создание обертки задачи для операции или события | `TaskFactory.FromAsync` или `TaskCompletionSource<T>` |
| Поддержка отмены задачи | `CancellationTokenSource` или `CancellationToken` |
| Прогресс выполнения | `IProgress<T>` и `Progress<T>` |
| Обработка потока данных | [TPL Dataflow](https://learn.microsoft.com/en-us/dotnet/standard/parallel-programming/dataflow-task-parallel-library) или [Reactive Extensions](https://github.com/dotnet/reactive) |
| Синхронизация доступа к разделяемым ресурсам | `SemaphoreSlim` |
| Асинхронная инициализация ресурсов | `AsyncLazy<T>` |
| Async-ready структуры публикации/подписки | TPL Dataflow или `AsyncCollection<T>` |
